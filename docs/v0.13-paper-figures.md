## 1. Purpose

Defines the figures and LaTeX tables that the paper §5 will use, the
aggregation rules behind them, and the parquet contract they require. This
serves two purposes:

1. **Contract for the relaunch.** The relaunch must produce a parquet with the
   columns, statuses, and grid coverage these figures need. If a relaunch
   finishes but a required column is empty, the run is incomplete.
2. **Contract for figure code.** The eventual plot-generation script must
   produce exactly these artifacts, with these aggregation rules and
   conditioning, so the paper's claims are defensible.

No code is written by this spec; it captures decisions made jointly with
Giovanni and locks them before implementation.

## 2. Parquet contract

Every cell run produces one or more rows in the v3 schema — **16 fields** on
`CellResult` (one row per (cell, query, metric)). The figures below consume:

- `benchmark`: `synthetic` | `scalability` | `bnlearn`
- `family`: **`discrete` | `continuous_gauss` | `clg`** (bnlearn); synthetic adds
  `continuous_nongauss` | `hybrid`
- `problem_id`: network name (bnlearn) | n_nodes-as-string (synthetic)
- `seed`: integer (bnlearn uses seed=1; DAG fixed, training data resampled)
- `baseline`: **single identifier string**, e.g. `nbn-cat-ve`, `pyro-cat-svi`,
  `pgmpy-mle-ve` (see parsing note below)
- `query_role`: `hub` | `cut` | `terminal` | `random` | `heaviest_hub` |
  `heaviest_cut` | `longest_propagation`

> **Sentinel rows have no role (#154).** Cell-level sentinel rows
> (`metric == "status"`: applicability, fit failure, worker death, problem
> generation failure) carry `query_role=""` — they describe a whole cell, not
> a query. Role decompositions must filter out `metric == "status"` rows
> before grouping by `query_role`; the role values above are emitted only on
> per-query rows. (Rows written before the #154 fix carry the placeholder
> `query_role="random"` on sentinel rows instead — filter by
> `metric == "status"`, which is correct for both old and new parquets.)
- `metric`: **accuracy metrics only** — `tv_per_node` | `jsd_per_node` |
  `w1_per_node` | `log_likelihood`
- `value`: numeric (NaN allowed for `not_supported`)
- `status`: `ok` | `not_supported` | `timeout` | `error` | `oom`
- `fit_time_s`, `query_time_s`, `metrics_time_s`: **dedicated timing columns**
  (repeated per-cell across that cell's rows; the #107 timing fix)
- `error_msg`: nullable; populated for non-`ok` rows
- `query_kind`: `prediction` | `diagnosis`
- `evidence_strategy`: `longest_path` | `mb_neighbors` | `random`
- `evidence_mode`: `full` | `empty`

> **Spec correction.** The original draft assumed (a) 14 columns, (b) separate
> `library`/`mechanism`/`inference_method` columns, (c) `family ∈ {discrete,
> clg, gbn}`, (d) a `size` column, and (e) timings as `metric` values. Reality:
> 16 fields; a single `baseline` string (no split columns); bnlearn `family ∈
> {discrete, continuous_gauss, clg}` (no `gbn`; gaussian → `continuous_gauss`);
> **no `size` column** (see §4.1); and the three `*_time_s` are dedicated
> columns while `metric`/`value` hold accuracy metrics only.

### 2.1 Baseline-string parsing

`baseline` is a hyphen-joined identifier (`<library>-<variant...>`, e.g.
`nbn-cat-ve`, `pgmpy-mle-ve`, `pomegranate-discrete-ve`). The figure code:

- treats `baseline` as an **opaque ID for filtering / grouping** (one bar per
  distinct `baseline`);
- **parses only the first hyphen-token as `library`** (`nbn` | `pgmpy` |
  `pomegranate` | `pyro`) to drive the grouped-by-library color scheme (§5.1).

The remaining tokens (mechanism / param-method / inference) are *not* a clean
fixed 3-tuple across libraries (e.g. pgmpy encodes a param-method, `mle`/`bayes`,
where nbn encodes a mechanism, `cat`), so they are used only as label text, never
parsed into structured columns.

### 2.2 Derived (non-column) attributes

- **`size_class`** — `small` | `medium` | `large` | `very_large` | `massive`,
  looked up from `nbn/bench/problems/bnlearn.py::_NETWORKS[problem_id]`. **Not
  a parquet column**; figure code joins it from the registry on `problem_id`.
- **`n_nodes`** — registry metadata (informational); join from `_NETWORKS` on
  `problem_id`.
- **`n_parameters`** — neither a column nor in the registry; derive at figure
  time (§5.4).

## 3. Aggregation contract

### 3.1 The aggregation flag

The figure code accepts a single flag: `--aggregation ∈ {mean_std, iqm_iqr}`,
propagated uniformly to every numeric aggregation — accuracy AND time — so a
paper section uses one consistent statistic throughout.

- `mean_std`: central = arithmetic mean; band = one standard deviation.
- `iqm_iqr`: central = interquartile mean (mean of values in [Q1, Q3]); band =
  half-IQR ((Q3 − Q1) / 2) around the IQM for symmetric rendering.

IQM reference: Agarwal et al., "Deep RL at the Edge of the Statistical
Precipice" (2021). Paper default: see §9.

### 3.2 Band clipping (the "no negative time" rule)

Bands drawn via `fill_between` respect each metric's natural range, clipped at
draw time (after aggregation; the unclipped value still goes in the table):

- **Time metrics (`*_time_s`, total query time)**: clip lower edge at 0.
- **`tv_per_node` / `jsd_per_node`**: clip at [0, 1] (TV ≤ 1; JSD reported / log 2
  so ≤ 1). Lower is better.
- **`w1_per_node`**: nonneg, no upper bound; clip at 0. Lower is better.
- **`log_likelihood`**: **unbounded, higher is better** — a score, not a
  distance. No clipping. Render with the opposite "good direction" from the
  distance metrics (annotate axes accordingly).
- **Success rate**: [0, 100%].

> **Spec correction.** `log_likelihood` added as a fourth accuracy metric. It is
> the one "higher is better, unbounded" metric — figure/table code must not clip
> it and must not assume "lower is better" when sorting/coloring.

### 3.3 Conditioning rule (Policy 3)

Every numeric figure uses a two-channel structure:

1. **Success-rate plot always shown**, computed on ALL rows for the cell. y-axis
   0–100%.
2. **Accuracy / time plots conditioned on `status == "ok"`.** Aggregation
   operates only on succeeded rows. Shown when success_rate > 0; when
   success_rate == 0 for a (baseline × cell), that baseline is missing/grayed in
   the accuracy/time plots, **not** drawn as zero.

Reader-facing implication: a method that fails on a network shows the failure in
its success-rate bar and is absent from the accuracy plot — so "fast and
accurate on 1/5 seeds" never visually reads as "…on 5/5 seeds."

### 3.4 Total query time definition

For each (`baseline`, `problem_id`, `seed`) where `status == "ok"`:

1. Sum `query_time_s` across all queries for that tuple → per-seed total.
2. Aggregate (per flag) those per-seed totals across seeds for the
   (baseline × problem) cell.
3. Band reflects across-seed variability of the per-seed totals.

"Total time for one full pass of queries on this problem, aggregated across seed
runs" — NOT a single sum-over-everything number.

## 4. Decomposition structure

### 4.1 bnlearn

bnlearn splits along **family** (`discrete` | `continuous_gauss` | `clg`) and a
**derived `size_class`** joined from `_NETWORKS` on `problem_id`.

> **Spec correction.** `size_class` has **5** registry values
> (small/medium/large/very_large/massive), not 3, and is not a parquet column.
> Per the planning decision, headline figures collapse to **3 buckets**:
> `small`, `medium`, `large+` (= `large ∪ very_large ∪ massive`). The full
> 5-bucket split is preserved for the **supplementary** appendix.

> **v0.14 update (PR-2).** The **size decomposition below is removed**. Figures
> and tables are now produced **per family only** (equivalent to the former
> `overall` bucket), with the size story carried by the `n_nodes` / `n_parameters`
> scaling x-axes (§5.4) rather than discrete size buckets. The family × network
> coverage table is retained for reference, but no per-size cells are emitted.

Headline decomposition, per family:

- size bucket ∈ {`small`, `medium`, `large+`} **plus** an `overall` bucket
  (aggregates all sizes for that family — the headline cell for the family's
  story).

**Not every (family × size) cell has networks.** From `_NETWORKS`:

| family | small | medium | large+ |
|---|---|---|---|
| discrete | ✓ (asia, cancer, earthquake, sachs, survey) | ✓ (alarm, barley, child, insurance, mildew, water) | ✓ (hailfinder, hepar2, win95pts, andes, diabetes, link, munin1/2/3/4, pathfinder, pigs, munin) |
| continuous_gauss | — *(empty)* | ✓ (ecoli70, magic-niab) | ✓ (magic-irri, arth150) |
| clg | ✓ (healthcare, …) | ✓/— *(registry-dependent)* | ✓/— *(registry-dependent)* |

**Figure-cell math (headline):** up to 3 families × 4 buckets (small, medium,
large+, overall) = **up to 12 cells per figure type**. **Cells with zero
networks are skipped** — no empty figures emitted (e.g. `continuous_gauss ×
small`). The exact non-empty count is determined at figure time by the join with
`_NETWORKS`; the figure script must log every skipped (family, size) cell so the
coverage is explicit rather than silently thinned.

Per cell, the figure types (§5) are: 1 success-rate + up to 4 accuracy
(tv/jsd/w1/log_likelihood, minus those with no `ok` rows; `w1_per_node` skipped
for `discrete` — see §5.2) + 1 total-query-time + 2 scaling = up to ~8 artifacts.

### 4.2 Synthetic

Synthetic uses the family/size taxonomy in
`nbn/bench/problems/synthetic.py` (families include `continuous_nongauss`,
`hybrid`). Same per-family-per-size + `overall` decomposition + skip-empty rule
applies. Specific buckets TBD when synthetic is relaunched — out of scope for
the immediate bnlearn_paper relaunch.

## 5. The four figure types (per family)

> **v0.14 layout (PR-4, supersedes PR-2).** Figures + tables are produced
> **per family**, and within each family split into auto-discovered **coverage
> subsets**. The per-size decomposition and its `<bench>/<family>/<size>/` tree
> were removed in PR-2; PR-4 nests subset folders under each family:
>
> ```
> <output_dir>/<benchmark>/<family>/
>   all/                  every problem, every supported baseline (mixed coverage)
>     plots/   success_rate.pdf, <metric>_vs_<axis>.pdf,
>              {total_query_time,fit_time}_vs_<axis>.pdf
>     tables/  table_overall.tex, table_kind_<k>.tex, table_role_<r>.tex
>   common/               problems solved by the FULL supported baseline set
>     methods.txt, problems.txt, plots/ (no success_rate.pdf), tables/
>   subsetN/              one per auto-discovered solving-baseline set
>     methods.txt, problems.txt, plots/, tables/
>   _subsets_overview.txt navigation aid
> ```
>
> A **subset** groups the problems whose *solving set* — the baselines that are
> `ok` on every row of the problem — is identical. It is named `common` when the
> solving set equals the full supported set, else `subsetN` (numbered by
> descending baseline-count, then problem-count, then alphabetically — fully
> deterministic). Subsets are **auto-discovered, not configured**; `methods.txt`
> and `problems.txt` (sorted, diffable) record each subset's membership.
> Problems no baseline fully solves are skipped (in no subset). Subset views omit
> `success_rate.pdf` (100% by construction). Filenames carry **no** `<family>_`
> prefix (the folder path names the family and subset). Table labels are
> `tab:<bench>_<family>_<subset>_<scope>`.
>
> `n_nodes` is resolved from the parquet column (PR-1 #195) with a `_NETWORKS`
> (bnlearn) / `int(problem_id)` (synthetic) fallback for older parquets, so a
> parquet that predates PR-1 still plots (an `info` line records the fallback).
> The `<metric>_vs_n_parameters.pdf` file is **skipped** when that family's
> `n_parameters` are all zero (e.g. `continuous_gauss`) — a degenerate x=0 axis
> (decision α).

X-axis grouping throughout: **one entry per distinct `baseline`**, ordered
grouped-by-`library` (first hyphen-token), consistent shades within a library.

### 5.1 Status-breakdown bar chart (100%-stacked)

- **Shows**: full status decomposition per `baseline` as a 100%-stacked bar —
  each bar sums to 100% and is split into `ok` / `not_supported` / `timeout` /
  `error` / `oom` segments. The `ok` segment is exactly the old success rate;
  the remainder shows *why* the rest failed. **Always shown** (no conditioning).
- **Counting unit**: same denominator as the success rate — one executed query
  (`metric == "query_time_s"` rows) plus whole-cell sentinel rows
  (`metric == "status"`, e.g. `not_supported` applicability and fit failures).
- **Y-axis**: 0–100%. **Not** subject to `--aggregation` (it's a proportion).
- **Color (legend)**: `ok` green, `not_supported` gray (applicability, not
  failure), `timeout` orange, `error` red, `oom` brown. Only statuses present
  in the cell appear in the legend. Stacking order is bottom-up: `ok` from the
  floor, failures above.
- **Filename**: `plots/<family>_success_rate.pdf`

### 5.2 Accuracy plots (one per metric)

One plot per metric in `{tv_per_node, jsd_per_node, w1_per_node, log_likelihood}`.

- `w1_per_node` is **skipped for `family == discrete`** (Wasserstein-1 N/A for
  discrete posteriors — those rows are `not_supported`, yielding empty
  conditioned data).
- `log_likelihood` is plotted **only where `metric == "log_likelihood"` rows
  exist** (parameter-learning-mode cells); skipped otherwise. Higher is better
  (§3.2) — axis annotated opposite to the distance metrics.

- **Conditioning**: shown only when success_rate > 0 for the baseline in this
  cell (§3.3).
- **Y-axis**: metric value, clipped per §3.2 at draw time.
- **Central value + band**: per `--aggregation`.
- **Filename**: `plots/<family>_<metric>_vs_<axis>.pdf` (one per `axis ∈
  {n_nodes, n_parameters}`; the `n_parameters` file follows the all-zero skip).

> **Spec correction.** `log_likelihood` is the added 4th accuracy plot; it is
> PL-mode and direction-flipped, so it is gated on row existence and rendered
> with inverted "good direction."

### 5.3 Total query-time plot

- **Shows**: total query time per (baseline × problem), aggregated per §3.4.
- **X-axis**: baselines (grouped-by-library), aggregating across problems-in-cell
  and seeds.
- **Y-axis**: total seconds (linear; switch to log if dynamic range across
  baselines exceeds ~2 orders of magnitude).
- **Conditioning**: shown when success_rate > 0. Band clipped at 0.
- **Filename**: `plots/<family>_total_query_time_vs_<axis>.pdf` (plus
  `plots/<family>_fit_time_vs_<axis>.pdf` for fit time).

### 5.4 Scaling curves (two per cell)

**5.4a — query time vs `n_nodes`** (resolve_n_nodes: parquet column → fallback):
- **X**: number of nodes (log-log preferred for the asymptotic story).
- **Y**: total query time per problem (§5.3), conditioned on `status == "ok"`.
- One line per baseline, fill-between band clipped at 0.
- **Filename**: `plots/<family>_total_query_time_vs_n_nodes.pdf`

**5.4b — query time vs `n_parameters`**:
- **X**: `sum(K_node × prod(K_parents) for node in problem.variables)` — a proxy
  for actual compute, more sensitive to cardinalities than `n_nodes`.
- Otherwise identical to 5.4a; **skipped** for all-zero families (decision α).
- **Filename**: `plots/<family>_total_query_time_vs_n_parameters.pdf`

Complementary stories: `n_nodes` is intuitive "problem size"; `n_parameters`
reflects what inference actually chews through. Same-node-count, different-card
networks (barley vs alarm) sit together on 5.4a but far apart on 5.4b.

**Implementation note (resolved).** `n_parameters` (#133) and `n_nodes` (PR-1
#195) are now problem-level parquet columns computed at problem-build time and
injected by the runner. The figure script reads them directly; older parquets
lacking `n_nodes` fall back via `resolve_n_nodes`.

## 6. LaTeX tables

For each (benchmark × family) cross, one copy-paste `\begin{tabular}` block, one
row per `baseline`, columns:

| Method (`baseline`) | Success % | TV | JSD | W1 | log L | Total time (s) |

(Accuracy columns formatted `central±band` per the flag, e.g. `IQM±IQR` or
`mean±std`.)

Rules:
- success_rate == 0 → `--` (em-dash) in accuracy and time columns.
- `W1` column omitted entirely for `family == discrete`.
- `log L` column shown only when the family/cell has `log_likelihood` rows
  (otherwise omitted); remember it is higher-is-better.
- Numeric formatting: 3 significant figures or 3 decimals (whichever is more
  informative); times in seconds.

Per family (v0.14 PR-2): one **overall** table (metric × role cross), plus one
table per `query_kind` and one per `query_role`. The per-size tables are
removed.

Filenames (each a full `table` float with `\caption` + `\label`, PR #189):
`tables/<family>_table_overall.tex`, `tables/<family>_table_kind_<k>.tex`,
`tables/<family>_table_role_<r>.tex`. Labels: `tab:<bench>_<family>_<scope>`.

## 7. Coverage requirements for the relaunch

See [docs/v0.13-oracle-methodology.md](v0.13-oracle-methodology.md) for the
oracle definition and noise-floor argument underlying all accuracy metrics.

The relaunch parquet must satisfy:

1. **All 16 CellResult fields populated** per row (only `error_msg` null for
   `status == "ok"`).
2. **Complete grid attempted**: for every (baseline × network × seed × query)
   tuple in the config, a row exists (even `not_supported` / `oom`). No silently
   dropped cells.
3. **Status taxonomy correctness**:
   - Cardinality/shape errors (Bug 1a class) absent post-Bug-1a.
   - OOM events classify as `oom`, not `error` (post-Bug-4).
   - Pyro on non-topological variable order shows no systematic failure
     (post-Bug-5).
   - barley + `nbn-cat-ve` hub-given-MB produces `ok` rows (post-Bug-2).
4. **`family` present on every bnlearn row**; **`size_class` derivable** from
   `problem_id` via `_NETWORKS` (it is not a parquet column — §2.2).

> **Spec correction.** Original §7 required a `size` label on every row; reality
> is that `size_class` is registry-derived, so the requirement is "`problem_id`
> resolves in `_NETWORKS`," not "`size` column present."

5. **`n_nodes` derivable** from `problem_id` via `_NETWORKS`. (`n_parameters`
   TBD per §5.4 — a figure-generation concern, not a relaunch blocker.)

A relaunch violating (1)–(4) is incomplete and must be re-run after diagnosis.
(5) is a figure-generation concern.

## 5b. Batch-speed figure (v0.14, #148)

Added by PR 6 of the batched-queries sequence
(docs/v0.14-batched-queries-design.md §6.PR6). Rendered by
`fig_batch_speed` in `nbn/bench/_paper_figures.py`.

- **Purpose:** the §5 batching claim — how amortized per-query inference
  time falls as the adapter processes more queries per library call.
  Supports "NBN's batched inference amortizes per-query cost; sequential
  baselines cannot."
- **Data source:** the parquet of a `batch_sizes`-sweep run
  (`nbn/bench/configs/synthetic/speed/inference_speed.yaml`; smoke:
  `inference_speed_smoke.yaml`).
- **Detection:** `nbn-bench plot` renders this figure automatically when
  the parquet has any row with `batch_size > 1`. Non-sweep parquets are
  unaffected.
- **Axes:** x = `batch_size` (log₂ scale), y = amortized per-query time
  in seconds (log scale, `query_time_s = batch_call_time / B` per design
  doc §1.6). One line per baseline; one facet per family, shared y-axis.
- **Filtering:** `status == "ok"` and `metric == "query_time_s"` rows
  only; non-positive/NaN values dropped.
- **Aggregation:** two-level — mean over a cell's queries per seed,
  then the standard `iqm_iqr`/`mean_std` aggregation across seeds for
  the line center and shaded band (same `aggregate()` as every other
  figure; band clipped non-negative).
- **DNF handling (matches the #163 convention):** error/timeout/oom
  rows are counted per (family, baseline, batch_size, status); each
  affected facet carries a corner note ("DNF: N cells") and the detail
  goes to a `batch_speed_dnf.txt` sidecar next to the figure. Expected
  at paper scale: non-batchable baselines (pyro, pgmpy) DNF at
  n_batch_queries=10240 under the 600 s cell budget (design doc §8.1) —
  that is by design, not a failure of the run. Baselines simply absent
  at swept values (pinned to batch_size 1 per §5.6) are *not* DNF.
- **File location:** `<output-dir>/<benchmark>/batch_speed.pdf` — at the
  benchmark level of the output tree (it is family-faceted internally,
  unlike the per-family/size figures of §5).
- **Reading guide (for §5 drafting):** a downward-sloping line =
  batching speedup (per-query cost amortizes as B grows); a horizontal
  line = no batching benefit; the horizontal B=1-only points of
  pyro/pgmpy are the sequential reference floor. The gap between an
  nbn line at B=1024 and its own B=1 point is the headline speedup
  factor; the gap to the pgmpy reference is the cross-library claim.

- **Aggregation default**: `mean_std` or `iqm_iqr`? Recommendation: `iqm_iqr` for

- **Method ordering**: grouped-by-library with consistent within-library shades

- **Headline table**: per-family currently; the paper may also want a top-level

## 10. What this commits us to

After the relaunch, figure generation has a clear contract:
- Read the parquet; join `size_class` / `n_nodes` from `_NETWORKS` on
  `problem_id`.
- Compute the four figure types per decomposition cell (§5), skipping empty
  cells (§4.1).
- Apply the aggregation flag (§3.1) and conditioning rules (§3.3).
- Emit LaTeX tables (§6).
- Produce a directory of `.png` / `.pdf` / `.tex` named per §5.

If the parquet satisfies §7, this is a straightforward pandas + matplotlib
script.

## 11. Invocation

The implementation is the `nbn-bench plot` subcommand
(`nbn/bench/_paper_figures.py::run_plot`), the second phase of the
benchmark → figures workflow:

```
nbn-bench inference --config nbn/bench/configs/bnlearn/smoke_tests/inference_smoke.yaml   # -> parquet
nbn-bench plot <results-dir-or-parquet> --output-dir <out> [--aggregation iqm_iqr|mean_std]
```

The `plot` parquet argument accepts either a `*_metrics.parquet` file or a
results directory (the `*_metrics.parquet` inside is found automatically).

`scripts/make_paper_figures.py` remains as a backward-compatible shim that
delegates to the same entry point and emits a `DeprecationWarning`; prefer
`nbn-bench plot`.
