# Runner subprocess isolation — design draft

**Status:** Design draft (pre-implementation)
**Tracker:** #127 (Bug 4)
**Related:** #109 (v0.13 roadmap), commit 048ff29, docs/v0.13-nbn-cat-ve-investigation.md

## 1. Background

The first paper-scale `bnlearn_paper.yaml` run crashed at the barley
network when nbn-cat-ve attempted a 612 GB allocation. The Linux
OOM-killer fired SIGKILL on the runner process, terminating the entire
benchmark. All in-progress cells were lost; the 23,675 rows of usable
data only survived because the existing runner writes JSONL
incrementally on completion of each cell.

The fundamental issue is architectural: the runner has no failure
boundary smaller than the entire benchmark. A single bad baseline on
a single problem can take down the entire multi-day run. This affects
not just nbn-cat-ve but any baseline that may exhaust memory on large
networks (munin*, link, andes) or trigger an unexpected fault.

This design adds subprocess isolation so any cell failure — exception,
timeout, SIGKILL — is contained. The runner records the failure as a
status row and continues.

## 2. Goals + non-goals

### Goals
- A SIGKILL of any single cell does NOT kill the runner.
- A subprocess crash produces a status row (`ok` / `error` / `timeout`
  / `oom`) and the runner continues to the next cell.
- Cell-level results survive: subprocess writes results that the
  parent then appends to the main metrics.jsonl, so partial writes
  during subprocess death don't corrupt the main file.
- The Phase 3 query-level soft timeout pattern is preserved.
- Compatible with existing YAML configs — no schema change required.

### Non-goals (out of scope for this PR)
- Parallel execution: one subprocess at a time, sequentially.
- Bug 3 (the CUDA-only in-process memory guard) — addressed in a
  follow-up if needed; subprocess isolation alone is sufficient for
  safety.
- Resuming from a partially-run benchmark — existing incremental JSONL
  handles "completed cells survive crashes"; mid-cell failures still
  mean re-running that cell on retry.
- Process pool / queue dispatcher — not needed for sequential execution.

## 3. Architecture

### 3.1 Failure containment boundary: B-cell

One subprocess per `(problem, baseline, seed)` cell. The full sequence
for a benchmark run becomes:
for problem in problems:
for baseline in baselines:
for seed in seeds:
cell_result = run_cell_in_subprocess(problem, baseline, seed)
append_to_main_jsonl(cell_result)

Sequential execution, no parallelism. For a paper-scale run
(~30 networks × 7 baselines × 5 seeds ≈ 1,000 cells), subprocess
launch overhead is ~200 ms each ≈ 3 minutes total — negligible
against a multi-day benchmark.

The cell-level granularity means:
- Maximum data loss from any single failure: one cell.
- The query-level work within a cell stays in the subprocess; query
  sampling, evidence selection, and per-query soft timeouts (Phase 3)
  happen there.
- Adapter `fit()` happens once per cell (not amortized across seeds).
  Slight overhead vs. fit-once-per-(problem, baseline), but the
  isolation is worth it.

### 3.2 Communication: file-based, temp-then-append

Each subprocess writes its results to a temp JSONL file. After the
subprocess exits (or is killed), the parent reads the temp file and
appends its contents to the main `metrics.jsonl`.

Why file-based:
- A subprocess that dies mid-write leaves a partial temp file. The
  parent can inspect it: complete lines are usable, the final partial
  line (if any) is discarded.
- Direct write to the main JSONL would risk corrupting the main file
  on subprocess death.
- Matches the existing incremental-JSONL pattern.

Layout per cell:
/tmp/nbn_cell_<run_id>_<cell_idx>.jsonl

`<run_id>` matches the benchmark's existing output directory naming
to prevent collisions across concurrent runs.

The parent appends only after the subprocess exits, so the main
`metrics.jsonl` only ever sees fully-buffered writes.

### 3.3 Status taxonomy

Existing statuses (from Phase 3): `ok`, `not_supported`, `error`,
`timeout`, `oom`.

New behavior per status:

| Status | Source | Cause |
|---|---|---|
| `ok` | subprocess exits 0 with all queries complete | normal completion |
| `error` | subprocess raises catchable exception, exits 0 with status=error in row | adapter raises a Python exception |
| `timeout` | parent SIGTERM after `per_cell_timeout_s` | cell exceeded total budget |
| `oom` | subprocess exits with signal SIGKILL (return code -9 / 137) | OS killed; assume OOM |

The `oom` classification follows the K3 convention: any SIGKILL is
recorded as `oom`, since the OS only SIGKILLs for memory exhaustion
or explicit user kill (and manual kills are not a normal-operation
concern). Misclassifying a manual `kill -9` of the benchmark is
acceptable.

If the subprocess exits with a non-zero return code that isn't a
signal (e.g., uncaught error reaching `sys.exit(1)`), parent records
`error` with the exit code in `error_msg`.

### 3.4 Timeout handling: two-level

**Cell-level** (existing): `per_cell_timeout_s` in YAML configs is the
hard ceiling. Parent SIGTERMs the subprocess if exceeded. After
SIGTERM, parent waits a short grace period (3-5 seconds) for cleanup;
if still alive, escalates to SIGKILL. Status: `timeout`.

**Query-level** (Phase 3, preserved): the subprocess maintains a
cumulative budget across queries. Per-query check before next query;
NaN recorded for timed-out `query_time_s`. The 10× fit-time safety
net from Phase 3 still applies.

The cell-level timeout is the parent's responsibility; the query-level
timeout is internal to the subprocess. They compose: a slow cell that
exhausts its query budget early on hard queries can still continue
processing easy queries until it hits the cell-level wall.

### 3.5 Per-cell memory cap

Subprocess isolation alone is not safe-by-default: a baseline that
attempts an enormous allocation can trigger the kernel OOM-killer,
which kills processes by reclaim priority — not necessarily the
offending subprocess. During Stage 4 development, a real test of
this scenario killed the developer's editor and several unrelated
processes before the runner subprocess was itself killed. The host
system survived but was destabilized for several minutes.

The fix is a per-cell virtual-memory cap, enforced inside the
subprocess via `resource.setrlimit(RLIMIT_AS, ...)`. The cap is
derived automatically:

- Anchored to `psutil.virtual_memory().available` (currently-free
  memory at cell launch time), not `.total` (hardware ceiling).
  This respects concurrent processes — editor, browser, OS — by
  leaving them headroom.
- 80% of available memory by default.
- 2 GB floor (anything tighter and the cell is going to fail anyway,
  so use a default that gives the cell a chance).
- Recomputed fresh per cell so it adapts to drift over a long run
  (parent state accumulates, other processes come and go).
- No YAML knob: the auto-derivation is the policy. If override is
  ever needed, the field can be added later. YAGNI.

Communication path:

1. `cell_runner._compute_cell_memory_limit_bytes()` derives the cap.
2. Parent passes it to the subprocess via the environment variable
   `NBN_CELL_MEMORY_LIMIT_BYTES`.
3. `cell_worker._apply_memory_limit()` reads the var and applies
   `RLIMIT_AS` (soft + hard) on itself before reading the input
   pickle or doing any other work.
4. Failures (non-POSIX platforms, existing lower limit, insufficient
   privilege) are swallowed — this is defense-in-depth, not a
   correctness requirement.

Behavior change for the OOM scenario:

- Before: a 612 GB allocation by nbn-cat-ve on barley would succeed
  via Linux overcommit, then paging would exhaust physical memory
  and the OS-killer would fire SIGKILL on whatever process the
  kernel deemed most expendable (in practice: large processes like
  the IDE).
- After: the cell subprocess hits the RLIMIT_AS ceiling at ~80% of
  available memory (e.g., 42 GB on a 61 GB laptop with 53 GB free).
  The kernel SIGKILLs the subprocess specifically. The parent
  records `status=oom` and continues. Other host processes are
  untouched.

This converts subprocess isolation from "nominally present" to
"safe by default for production use."

## 4. Subprocess interface

### 4.1 Parent-side: cell launcher

A new function (probably `benchmarking/core/cell_runner.py`):

```python
def run_cell_in_subprocess(
    problem: BenchmarkProblem,
    baseline_spec: BaselineSpec,
    seed: int,
    selector_config: dict,
    per_cell_timeout_s: float,
    output_dir: Path,
) -> list[CellResult]:
    """Run one cell in a subprocess. Returns the result rows."""
```

Implementation sketch:
1. Serialize `problem`, `baseline_spec`, `seed`, `selector_config` to a
   pickle file at `/tmp/nbn_cell_input_<run_id>_<cell_idx>.pkl`.
2. Compute the output temp file path.
3. `subprocess.Popen(["python", "-m", "benchmarking.core.cell_worker", input_path, output_path], ...)`.
4. Wait up to `per_cell_timeout_s` for completion. SIGTERM if exceeded;
   wait 3s grace; SIGKILL if still alive.
5. Read the output JSONL file; parse complete lines into `CellResult`
   rows. Discard partial final line if subprocess died mid-write.
6. If the temp file is empty (subprocess died before any write),
   produce a single synthetic row with `status=oom` or `status=error`
   depending on the exit code.
7. Clean up input + output temp files.
8. Return result rows.

### 4.2 Subprocess-side: cell worker

A new module (probably `benchmarking/core/cell_worker.py`):

```python
def main():
    """Entry point for the cell worker subprocess.

    Args: input_pickle_path output_jsonl_path
    """
    input_path = sys.argv[1]
    output_path = sys.argv[2]

    with open(input_path, "rb") as f:
        ctx = pickle.load(f)

    # Open the output file for append-as-we-go writing
    with open(output_path, "w") as out:
        # Build the adapter
        adapter = build_adapter(ctx["baseline_spec"])

        # Fit (the most likely OOM hotspot)
        try:
            adapter.fit(ctx["problem"])
        except Exception as e:
            for row in build_fit_error_rows(ctx, e):
                out.write(json.dumps(row.as_dict()) + "\n")
                out.flush()
            return

        # Run queries — Phase 3 soft-timeout-per-query logic preserved
        for query in select_queries(ctx):
            result_row = run_one_query_with_soft_timeout(adapter, query, ctx)
            out.write(json.dumps(result_row.as_dict()) + "\n")
            out.flush()
```

Critical: `out.flush()` after every row. This is what ensures partial
data survives mid-cell death.

The existing query-loop code in the current runner is the basis for
`run_one_query_with_soft_timeout` — the Phase 3 soft-timeout pattern
moves wholesale into the worker. Minimal refactor.

## 5. Integration with the existing runner

The current `Runner.run()` (in `benchmarking/core/runner.py`) has
roughly this shape:

```python
for problem in problems:
    for baseline in baselines:
        for seed in seeds:
            # current: in-process call to AccuracyAndTiming.measure(...)
            rows = measurement.measure(adapter, problem, queries, ...)
            for row in rows:
                jsonl_writer.write(row)
```

After this change:

```python
for problem in problems:
    for baseline in baselines:
        for seed in seeds:
            # new: subprocess call
            rows = run_cell_in_subprocess(problem, baseline, seed, ...)
            for row in rows:
                jsonl_writer.write(row)
```

The in-process measurement code moves into `cell_worker.main()`. The
runner becomes a thin orchestrator over subprocess calls.

### 5.1 What stays the same

- YAML config schema (no changes).
- Selector code (TopologicalAllocator, HeaviestQueryByRole) runs inside
  the subprocess.
- Measurement code (AccuracyAndTiming) runs inside the subprocess.
- Oracle code runs inside the subprocess.
- Parquet conversion happens in the parent after all cells complete
  (or on resume).
- Status taxonomy is unchanged at the row level.

### 5.2 What changes

- `Runner.run()` no longer calls `measurement.measure()` directly.
- A new `cell_worker.py` module exposes the worker entry point.
- A new `cell_runner.py` module contains the parent-side launch logic.

## 6. Testing strategy

The new code paths are inherently hard to unit-test because the value
proposition is "what happens when a subprocess dies." Tests:

### 6.1 Unit tests (fast)

- Cell input/output serialization round-trip.
- Output JSONL parsing tolerates a partial final line (subprocess died
  mid-write).
- Empty output file produces a synthetic `oom` or `error` row.
- Exit code → status mapping (-9 → oom, non-zero non-signal → error, 0 → ok).

### 6.2 Integration tests (slow)

- A "well-behaved" cell completes with `status=ok` rows in the output.
- A cell that allocates 100 GB intentionally is killed by OS; runner
  records `oom` and continues.
- A cell that sleeps forever is SIGTERM'd by parent after timeout;
  runner records `timeout`.
- A cell that raises a Python exception produces `status=error` rows
  with traceback in `error_msg`.

The "deliberate OOM" test uses `resource.setrlimit(RLIMIT_AS, ...)`
inside the test subprocess so the test runner itself doesn't OOM.

### 6.3 End-to-end smoke (slowest)

After implementation:
1. Run `bnlearn_smoke.yaml` (the existing 3-network smoke) and confirm
   identical output to pre-change behavior — same rows, same statuses.
2. Construct a "torture smoke" config with one network known to OOM
   (barley + nbn-cat-ve) and confirm:
   - The runner does NOT die.
   - The metrics.jsonl contains `status=oom` rows for the failed cells.
   - Other (problem, baseline, seed) cells complete normally.

## 7. Implementation plan (multi-stage PR)

### Stage 1: Cell worker + cell runner skeleton
- `benchmarking/core/cell_worker.py`: subprocess entry point
- `benchmarking/core/cell_runner.py`: parent-side launcher (build,
  spawn, wait, kill, read results)
- Unit tests for serialization round-trip, partial-line handling,
  exit-code → status mapping
- NO integration with `Runner.run()` yet — both modules importable
  but unused

### Stage 2: Wire into Runner
- Replace the in-process measurement call in `Runner.run()` with
  `run_cell_in_subprocess(...)`
- All existing fast tests pass unchanged
- bnlearn_smoke.yaml end-to-end produces identical output

### Stage 3: Failure-mode integration tests
- Add the deliberate-OOM, deliberate-timeout, deliberate-exception
  cells as integration tests
- Confirm runner survives each
- Confirm status rows are correct in the output

### Stage 4: Torture smoke + finalize
- Run a configurable subset of bnlearn_paper.yaml that includes barley
  (known to OOM)
- Confirm:
  - Runner completes
  - barley/nbn-cat-ve rows show `status=oom`
  - Other baselines on barley complete normally
  - Subsequent networks (other than barley) run normally
- Mark PR ready

## 8. Open questions for implementation

These are not blockers but worth flagging:

- **Pickle compatibility**: RESOLVED (Stage 1 verification). All
  problem variants, selectors, and measurements pickle cleanly.
  asia=18KB, ecoli70=64KB, synthetic=221KB.

- **Per-cell memory cap (RESOLVED, commit 7d1068d)**: subprocess
  sets RLIMIT_AS to 80% of available memory (2 GB floor) at startup.
  Auto-derived, no YAML knob. See §3.5.

- **GPU resources**: if a baseline uses GPU, subprocess startup needs
  to be CUDA-context-aware. For the current paper run (all CPU
  baselines), this isn't an issue. Flag for future work.

- **Subprocess Python import time**: a Python subprocess that imports
  the full nbn + benchmarking stack may take 1-3 seconds. For ~1,000
  cells, that's 16-50 minutes of import overhead. Could optimize via
  module preimport or persistent worker (a future improvement; the
  current plan accepts the cost).

- [ ] All failure modes (exception / timeout / OOM) produce status rows
