# nbn-cat-ve + pyro investigation — bnlearn_paper run, June 2026

**Status**: investigation complete; fixes pending per P2 plan
**Tracker**: #127
**Related**: #109 (v0.13 roadmap), commit dd5da0d (Phase 4 merge)
**Data**: `benchmarking/results/benchmark_bnlearn_bnlearn_paper_20260602_111920/metrics.jsonl`

## TL;DR

The first paper-scale `bnlearn_paper.yaml` run crashed at **barley** with a
**612 GB OS-killing OOM** in nbn-cat-ve. Investigation surfaced **four distinct
nbn issues** plus **one pyro fit-time bug**:

1. **Bug 1** — categorical cardinality truncation (correctness)
2. **Bug 2** — VE eliminates the whole network, no relevant-subnetwork pruning (the OOM root cause)
3. **Bug 3** — the memory guard is CUDA-only, so the CPU path is unprotected
4. **Bug 4** — the runner has no subprocess isolation, so a SIGKILL kills everything
5. **Bug 5** — pyro `KeyError` from non-topological fit iteration (correctness)

Crucially, **612 GB is not a structural treewidth limit**: barley's treewidth is
~7 and a *correct* VE for the failing queries needs ~0.001 GB. The OOM is a bug.

## Bug 1: CategoricalTableMechanism cardinality truncation

**Location**: `nbn/mechanisms/categorical_table.py:77-79`

```python
class_values = torch.unique(x, sorted=True)
k = int(class_values.shape[0])
self._n_classes = k
```

`fit_local` sets `n_classes` from the number of **observed-distinct** values in
the training sample, not the declared cardinality. On barley (max card 67, mean
8.77) with `n_train=10240`, 7/48 nodes truncate:

```
pesticid: declared=2 fitted=1     exptgens: declared=6 fitted=5
ngodnt:   declared=10 fitted=9    ngodnn:   declared=10 fitted=9
ngodn:    declared=10 fitted=9    nprot:    declared=8 fitted=7
spndx:    declared=4 fitted=1
```

Factors then disagree on a shared variable's axis size. Confirmed axis
disagreements:

```
factor[nprot]   axis 1 var ngodn:    physical=10 declared_card=9
factor[ngtilg]  axis 0 var ngodn:    physical=10 declared_card=9
factor[exptgens]axis 2 var pesticid: physical=2  declared_card=1
factor[nopt]    axis 0 var pesticid: physical=2  declared_card=1
```

(`factor[nprot]` carries parent `ngodn` at size 10 — its own fit saw value 9 in
the parent column → max+1=10 — while `ngodn`'s own factor is size 9.)

At query time this surfaces as the exact production errors (reproduced verbatim):

```
300x  RuntimeError: size of tensor a (10) must match b (9) at non-singleton dim 1
120x  IndexError: select(): index 1 out of range for tensor of size [1]
 60x  IndexError: select(): index 3 out of range for tensor of size [10,6,5,1] dim 3
```

matching the metrics.jsonl barley/nbn-cat-ve rows (294×/114×/96×…). These are
the **726 `error` rows** — all *caught* (not the OOM).

**Severity**: correctness — produces wrong answers even when it doesn't crash.

**Fix**: take `n_classes` from the declared cardinality (`problem.variables[node][1]`,
already threaded into the adapter); pad the CPT with the Dirichlet prior for
unobserved values.

## Bug 2: VE eliminates the entire network (no relevant-subnetwork pruning)

**Location**: `nbn/inference/tensor_ve.py:131-197` (single-row `query()`),
`nbn/inference/_elimination_order.py:84-129` (`min_fill_order`)

This is the **612 GB OOM root cause**.

### Not a structural limit

- barley: 48 nodes, **treewidth ≈ 7**, max cardinality 67, mean 8.77.
- Worst-case **marginal** min_fill peak (declared cards): **0.28 GB**.
- Successful queries in the repro peak at **0.27 GB**.
- OOM size: `614,515,507,200 bytes = 153,628,876,800 cells = 2¹³·3⁷·5²·7³` — a
  **~12-variable** factor, and notably with **no factor of 67 or 11**, i.e. a
  clique of *moderate*-cardinality nodes that have no business co-existing.

### The actual mechanism

Decisive test: query hub `aks_m2` (degree 8) given its **full Markov blanket**
(9 nodes) as evidence. The target is conditionally independent of everything
else given its MB — the answer is just its local CPD (≈0.001 GB). Yet nbn's VE
schedules **all 38** remaining variables for elimination, **38 of them
irrelevant** (barren / d-separated). With correct conditioning the peak is
**0.001 GB**.

Two compounding faults:
1. **No ancestral/Bayes-ball pruning** — VE eliminates every non-target,
   non-evidence variable, including barren and d-separated ones.
2. **`min_fill_order` adds fill edges for conditioned evidence**
   (`_elimination_order.py:123-129`). That is correct for *summed-out*
   variables but wrong for *observed* ones (conditioning slices, it does not
   couple neighbours), producing a pathological order over the irrelevant
   remainder.

Reproduced: hub/`mb_neighbors`/`diagnosis` queries attempted a **32 GB** single
allocation under an 8 GB `ulimit` cap (caught as a `RuntimeError`); production,
with abundant RAM, reached 612 GB. These are exactly the `query_role=hub`,
`evidence_strategy=mb_neighbors` rows in the metrics.

**Severity**: tractability — makes nbn-cat-ve unusable on real networks ≥ ~30
dense discrete nodes.

**Fix**: ancestral/Bayes-ball pruning before elimination (drop barren nodes and
nodes d-separated from the target by the evidence; restrict elimination to the
relevant subnetwork). Stop adding fill edges for conditioned evidence in
`min_fill_order`.

## Bug 3: Memory guard is CUDA-only

**Location**: `nbn/inference/tensor_ve.py:272-292`, gated on `device.type == "cuda"`

`_estimate_peak_bytes` exists **only in `query_batch`** and **only under CUDA**.
The adapter (`benchmarking/adapters/nbn_adapter.py:249`) uses the **single-row
`query()`** path on **`device="cpu"`** (default) — which has **no guard at all**.

The runner *can* classify a CPU allocator `RuntimeError` as `oom`
(`runner.py:110-113`, markers include `"can't allocate memory"`). But with
abundant RAM, `malloc(612 GB)` is granted via Linux overcommit; paging then
exhausts physical memory and the **OOM-killer fires SIGKILL** (uncatchable).
Consistent with **zero `oom` rows** anywhere in the metrics.

**Severity**: turns a recoverable `status=oom` into a catastrophic runner death.

**Fix**: move the guard out of the CUDA branch, compare against
`psutil.virtual_memory().available` on CPU, and apply it in the single-row
`query()` path too.

## Bug 4: Runner has no subprocess isolation

**Location**: `benchmarking/core/runner.py`

When a baseline cell SIGKILLs, it takes down the entire runner. Even after Bugs
1–3 are fixed, future surprise OOMs are inevitable. Current mitigation is only
the incremental JSONL write, which preserves completed cells but loses the
in-progress cell and all queued work.

**Severity**: architectural; affects all long-running benchmarks.

**Fix**: run each (problem, baseline, seed) cell in a subprocess. An OS kill
takes down the worker, not the runner; the parent records `status=killed` and
continues.

## Bug 5: pyro KeyError — non-topological fit iteration

**Location**: `benchmarking/adapters/pyro_adapter.py:156` (fit loop) →
`:191` (`pa_cards = [self._cards[p] for p in disc_parents]`)

**Verdict: D — not the cardinality/state hypothesis.**

pyro-empirical-importance produced 472× `KeyError('LVFAILURE')` on alarm and
135× `KeyError('Erk')` on sachs. `LVFAILURE` and `Erk` are **node names**, not
state values, and the adapter already reads declared cardinality from
`problem.variables` (line 156-158, `self._cards[node] = k`).

The real cause: `fit()` iterates `problem.variables.items()` (insertion order)
and populates `self._cards[node]` only as each node is processed.
`_fit_discrete_cpt` needs every discrete **parent**'s cardinality already in
`self._cards`. When a child is fitted before its discrete parent, the parent
lookup raises `KeyError(parent_name)`. This is a deterministic **fit-time**
failure → every query in the cell becomes a fit-failure sentinel row.

Confirmed:

```
alarm: child 'HISTORY' (var-order pos < 'LVFAILURE' pos 5) fitted first
       → KeyError('LVFAILURE'); 17 (child,parent) order-violations total
sachs: child 'Akt' fitted before parent 'Erk'
       → KeyError('Erk'); 15 violations
under TOPOLOGICAL iteration: 0 violations on both
```

The adapter already computes `self._topo` at line 153 but doesn't use it for the
fit loop.

**Severity**: correctness — pyro silently dies on any network whose
`problem.variables` order isn't already topological.

**Fix**: iterate `self._topo` in the fit loop (line 156) instead of
`problem.variables.items()`; or pre-populate `self._cards[node] = k` for all
discrete nodes before the CPT-building loop.

## Reproduction

All runs under an 8 GB virtual-memory cap so a runaway allocation raises a
catchable error instead of killing the host:

```bash
cd $(git rev-parse --show-toplevel)
ulimit -v 8000000   # 8 GB cap
```

### Bug 1 — cardinality truncation + the 726 errors

```python
from benchmarking.problems.bnlearn import BnlearnConfig, BnlearnProblemSource
from benchmarking.core.config import BaselineSpec, build_adapter

src = BnlearnProblemSource()
cfg = BnlearnConfig(networks=["barley"], seeds=[0],
                    n_train=10240, n_test=1024, n_reference=10240)
problem = next(src.iter_problems(cfg))
declared = {n: k for n, (_kind, k) in problem.variables.items()}

adapter = build_adapter(BaselineSpec(library="nbn", mechanism="cat",
                                     param_method="mle", inference_method="ve"))
adapter.fit(problem, epochs=1)
for n in problem.variables:
    f = adapter.model.mechanisms[n].n_classes
    if f != declared[n]:
        print(n, "declared", declared[n], "fitted", f)   # 7 nodes truncate
```

Running hub/`mb_neighbors`/`diagnosis` queries (target = highest-degree node,
evidence = its Markov blanket from test_data) reproduces the
`RuntimeError: tensor a (10) must match b (9)` and
`IndexError: select index out of range` errors verbatim.

### Bug 2 — eliminate-everything blowup

With the same `adapter`, hub/MB queries attempt a 32 GB single allocation
(caught by the 8 GB cap). The "should be trivial" proof:

```python
import networkx as nx
from nbn.inference._elimination_order import get_order
nodes = list(problem.variables)
dag = nx.DiGraph(); dag.add_nodes_from(nodes); dag.add_edges_from(list(problem.dag))
hub = max(nodes, key=lambda n: dag.degree(n))
mb = set(dag.predecessors(hub)) | set(dag.successors(hub))
for c in dag.successors(hub): mb |= set(dag.predecessors(c))
mb.discard(hub)
order = get_order("min_fill", dag, targets=[hub], evidence=list(mb))
print(len(order), "vars eliminated;", len(set(nodes)-({hub}|mb)), "are irrelevant")
# -> 38 eliminated, 38 irrelevant; correct VE peak ~0.001 GB
```

### Bug 5 — pyro non-topological fit

```python
from benchmarking.problems.bnlearn import BnlearnConfig, BnlearnProblemSource
from benchmarking.core.config import BaselineSpec, build_adapter

problem = next(BnlearnProblemSource().iter_problems(

```

## Why the smoke missed this

asia (8 nodes, max card 4), ecoli70 (Gaussian — doesn't exercise discrete VE),
and sangiovese (15 nodes) lack the high-cardinality + dense Markov-blanket
structure that triggers Bugs 1–2, and their `problem.variables` order happens to
be topological-compatible for pyro. The smoke needs at least one medium-large
discrete network with cardinalities ≥ 10 (and a non-topological variable order)
to catch this class of failure.
