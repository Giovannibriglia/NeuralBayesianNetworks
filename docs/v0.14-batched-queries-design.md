# Batched queries design (Changes 1 + 2)

**Target:** Issues #148 (speed benchmark) and #149 (auto-batch question).

**Decisions locked:**
- **Change 1**: across-the-board `n_batch_queries` parameter in selectors. Default 1 (existing benchmarks unaffected). When > 1, selectors emit query groups sharing (target, evidence_vars); adapters that can batch (nbn, pomegranate) use library batching; others loop sequentially. Per-query rows still emitted with `query_time_s = batch_time / B`.
- **Change 2**: new `batch_speed` benchmark — 1-2 problems per family, `n_batch_queries=10240`, sweeps `batch_size` ∈ {1, 64, 128, 512, 1024, ...}. NBN + pomegranate use library batching; pyro + pgmpy always batch=1. Closes #148.

**Why this shape:**
- Bnlearn / scalability benchmarks keep their per-query timing semantics (existing data + future relaunches unchanged)
- NBN's batched advantage is exercised in a dedicated, comparable-to-competitors benchmark
- Change 1's infrastructure makes Change 2 trivially expressible (just a new config)
- Both changes are additive; no existing behavior changes when `n_batch_queries=1` (the default)

**Date:** 2026-06-07 (post-bnlearn-pascal-failure-investigation, pre-bnlearn-laptop-relaunch)

## Section 1: API contracts (LOCKED 2026-06-07)

### 1.1 Two distinct parameters

- **`n_batch_queries`**: selector-level. Query *generation*. How many queries the selector emits per (target, evidence_vars) group. Default 1. Set to 10240 (or similar) only in the speed benchmark config.
- **`batch_size`**: adapter-level. Query *consumption*. How many queries the adapter processes per library call. Default 1. Set per-baseline in the YAML config (alongside `extra_kwargs`).

### 1.2 `BaselineAdapter` protocol

Add `query_batch(queries: list[Query]) -> list[Posterior]`:

```python
def query_batch(self, queries: list[Query]) -> list[Posterior]:
    """Process a list of queries; return Posteriors in input order.
    
    Adapters that support library-level batching override this.
    Default implementation (module-level helper) loops query() sequentially.
    
    Queries within a single call SHOULD share (target, evidence_keys).
    Selector (when n_batch_queries > 1) emits such groups; adapters MAY
    assume this for batching.
    """
```

Default helper (NOT a base class method — module-level function each adapter explicitly opts into or overrides):

```python
def default_query_batch(adapter, queries: list[Query]) -> list[Posterior]:
    return [adapter.query(q) for q in queries]
```

### 1.3 Selector returns `list[list[Query]]`

Outer list: groups sharing (target, evidence_keys). Inner list: queries within a group. With `n_batch_queries=1`, every inner list is length-1.

Selector also handles the chunking by `batch_size` (passed in from the runner / config). Each inner list returned has length ≤ `batch_size`. So:
- `n_batch_queries=10240, batch_size=512` → selector emits 20 inner lists of length 512 per (target, evidence_vars) group
- `n_batch_queries=1` → selector emits one inner list of length 1 (existing behavior)

### 1.4 Schema change: `batch_size: int` column

New column in `CellResult`. Default 1 for existing data (handled via parquet's null-fill on read). Set to the actual batch size used when the row was emitted.

### 1.5 YAML config — per-baseline `batch_size`

Example:
```yaml
baselines:
  - { library: nbn, mechanism: cat, inference_method: lw, extra_kwargs: { n_samples: 4096 }, batch_size: 512 }
  - { library: pyro, ..., batch_size: 1 }
```

Default if omitted: 1. Existing configs (bnlearn, scalability, smoke) don't need to change.

### 1.6 Per-query timing semantics

For a batch of `B` queries answered in `batch_call_time` seconds:
- Each emitted row: `query_time_s = batch_call_time / B`
- `metrics_time_s`: per-query (scorer runs per Posterior, sequential)
- `batch_size` column stamped with `B`

### 1.7 Speed benchmark config: single YAML with `batch_sizes` sweep

`nbn/bench/configs/synthetic/speed/inference_speed.yaml` contains a top-level `batch_sizes: [1, 64, 128, 512, 1024, ...]` field. The runner iterates this sweep, overriding each baseline's `batch_size` to the current sweep value for that pass. One run, one parquet, one set of figures.

Runner changes required:
- Detect `batch_sizes` top-level field
- For each value: override each baseline's `batch_size` (where the baseline supports batching) and run a full pass
- Non-batchable baselines (where YAML has `batch_size: 1` pinned) ignore the sweep — they only run once at batch_size=1, OR run at every sweep value with batch_size=1 (decide in §5)
- Resulting parquet has `batch_size` column populated across all rows

**Open question for §5 (speed benchmark design):** for non-batchable baselines (pyro, pgmpy), do they:
- (i) Run once total (at batch_size=1) and the speed figure shows their line as a flat reference; or
- (ii) Run once per sweep value (always at batch_size=1) — repeated work but the rows are present alongside the batchable baselines for each sweep value

Defer to §5.

## Section 2: Selector behavior (LOCKED 2026-06-07)

### 2.1 Strategy: sample evidence values from the problem's training dataset

For a query position `(target, evidence_vars)`, the selector generates `n_batch_queries` evidence-value combinations by sampling `n_batch_queries` rows from the problem's training dataset and reading off the values for `evidence_vars` columns from each row.

**Rationale:** the speed benchmark measures inference *speed*, not robustness to adversarial inputs. The workload should resemble what a deployed model would see. Strategy matches what bnlearn and scalability benchmarks already do (single-row evidence sampling from training data), just with `n_batch_queries` rows instead of 1.

Rejected alternatives:
- Uniform sampling over evidence variable supports: would hit low-probability evidence regions, cause degenerate posteriors under LW, contaminate timing measurements with rare-evidence handling overhead.
- Hybrid (mostly training + some uniform): more config knobs without clear benefit for a speed benchmark.

### 2.2 Sampling with replacement when n_train < n_batch_queries

If the problem's training dataset has fewer rows than `n_batch_queries`, sample with replacement. The duplication is acceptable because:
- The speed benchmark wants total work = `n_batch_queries` query evaluations
- Repeated identical evidence values still go through the same inference path
- For batchable adapters (nbn, pomegranate), duplicates within a batch don't cause correctness issues — they just produce identical posteriors

### 2.3 Group emission shape

Selector emits `list[list[Query]]`. For a selector configured with `n_batch_queries=N` and target `batch_size=B`:

1. Selector picks `K` query positions (target, evidence_vars combinations) per its existing logic (heaviest-by-role allocation, uniform-random, etc.)
2. For each query position, samples `N` rows from training data
3. Splits the `N` queries into chunks of size `B`, emitting one inner list per chunk
4. Outer list contains `K × ceil(N/B)` inner lists total

With `n_batch_queries=1` (existing benchmarks): emits `K` inner lists of length 1. Identical to current behavior.

With `n_batch_queries=10240, batch_size=512`: emits `K × 20` inner lists of length 512.

With `n_batch_queries=10240, batch_size=1`: emits `K × 10240` inner lists of length 1 (sequential, for pyro/pgmpy).

### 2.3.1 Formula reference

For a cell configured with:
- `n_queries_per_cell = K` (existing YAML parameter — selector query positions)
- `n_batch_queries = N` (new parameter, default 1)
- `batch_size = B` (new YAML field per baseline, default 1)

The selector emits:
- Total queries per cell: `K × N`
- Total parquet rows per cell: `K × N` (per-query rows, see §1.6)
- Total batch calls per cell: `K × ceil(N / B)`

With both N=1 and B=1 (existing benchmarks), this reduces to `K`
queries, `K` rows, `K` batch calls — identical to pre-Change-1
behavior.

### 2.4 Selectors affected

Both existing selectors get the new parameter:
- `HeaviestByRole` — `n_batch_queries` controls how many evidence-value variants per (role, kind) allocated query position
- `UniformRandomSelector` — same

The query-position selection logic is unchanged; only the per-position multiplicity changes.

### 2.5 Determinism

Sampling from training data uses the existing per-seed RNG. With the same seed, the same rows are sampled in the same order. Two runs of the speed benchmark with identical configs produce identical query lists.

## Section 3: Adapter implementations (LOCKED 2026-06-07)

### 3.1 nbn adapter — override `query_batch`

When `query_batch([q1, ..., qB])` is called with all queries sharing (target, evidence_vars):

1. Assert all share target and `frozenset(evidence_keys)` (selector contract; fail fast if violated)
2. Stack evidence: for each evidence variable `v`, build a `[B]` tensor from the B query values
3. Call `engine.query_batch(model, target, evidence_dict)` — nbn library's existing batched API
4. Split the `[B, ...]` posterior into B individual `Posterior` objects
5. Return as list in input order

**(V1 resolved 2026-06-07):** for LW continuous targets, the library's `LikelihoodWeightingEngine.query_batch` (`nbn/inference/likelihood_weighting.py:153`) returns per-row independent weighted samples — `(weights [B,S], samples [B,S,D])`. Per-row multinomial resampling already exists in the adapter for B=1 (`nbn_adapter.py:254-262`) and generalizes to 2-D `[B,S]` input via `torch.multinomial` for free. **The per-row resample step lives in the adapter, not the library.** PR 2 must add a missing LW batch-vs-looped equivalence test (the existing `test_vectorized_query_batch_correctness.py` covers VE only).

For discrete VE (`tensor_ve.py:273`): batched return is `[B, K]`, per-row independence is structural (exact inference, no sampling), already covered by the existing correctness gate at atol=1e-6.

### 3.2 pomegranate adapter — override `query_batch`

Override uses pomegranate's batched inference API.

**(V2 resolved 2026-06-07):** pomegranate 1.1.2 `BayesianNetwork.predict_proba(X)` takes a `torch.masked.MaskedTensor` of shape `(B, n)`, mask True = observed, False = missing. Docstring explicitly states "Different sets of variables can be observed or missing in different examples" — so per-row masks are supported, though for our shared-(target, evidence_vars) batches we just repeat the mask B times. Output: list of `n` tensors, one per variable, each `[B, K_var]`; we index `out[target_idx]`.

The current adapter (`nbn/bench/adapters/pomegranate_adapter.py:193-218`) already builds a `[1, n]` masked tensor for single queries — batching is literally stacking B rows with the shared mask repeated. Note: pomegranate's `predict_proba` is loopy BP — exact only on tree-like graphs (pre-existing limitation, not batch-specific).

### 3.3 pyro and pgmpy — default sequential

Use the module-level `default_query_batch` helper. With YAML `batch_size: 1` pin, selector emits length-1 inner lists; default helper loops `query()`; behavior identical to today.

### 3.4 Per-baseline batch_size, per-cell selector behavior

`batch_size` is a per-baseline YAML field. Selector is invoked per-cell (problem × baseline × seed), receives that baseline's batch_size, and chunks accordingly.

Consequence: in the speed benchmark with `batch_sizes` sweep, non-batchable baselines (pinned at `batch_size: 1`) only run ONCE — see §5 for the sweep dispatch logic.

### 3.5 Sweep dispatch for non-batchable baselines

**Decision: pyro/pgmpy run only at batch_size=1, once.**

In the speed benchmark sweep:
- Batchable baselines (nbn-*, pomegranate-*): run once per sweep value, each cell produces rows with `batch_size = sweep_value`
- Non-batchable baselines (pyro-*, pgmpy-*): pinned at `batch_size: 1` in YAML, run once total (during the first sweep iteration where their batch_size matches), produce rows with `batch_size = 1`

Speed-benchmark figure (log-log per-query time vs batch_size): non-batchable baselines appear as horizontal reference lines at their batch_size=1 value. Batchable baselines show downward-sloping curves.

## Section 4: Per-query timing semantics under batching (LOCKED 2026-06-07)

### 4.1 Success case

Batch of B queries → single library call → `batch_call_time` measured → B Posterior objects returned. Per-query rows emitted:
- `query_time_s = batch_call_time / B` (amortized)
- `batch_size = B`
- `metrics_time_s`: per-row (scorer runs per Posterior, sequential)
- `status = "ok"`

### 4.2 OOM case — atomic batch failure (α)

If the batch call raises OOM (CUDA OOM, MemoryError, allocation failure): all B rows get `status = "oom"`, `query_time_s = NaN`, `batch_size = B`, `metrics_time_s = NaN`. No per-row retry; no adaptive halving. Atomic batches = atomic outcomes.

Rationale: simplicity (no adapter fallback logic), honest representation (the batch failed; recording B "individual" outcomes is misleading), the sweep itself is the adaptive mechanism (if B=1024 OOMs, B=512 will retry).

### 4.3 Timeout case — cumulative per-cell timer

The runner's existing `per_cell_timeout_s` is a cumulative cell-level timer (PR #129 isolation handles SIGKILL). With batching, the timer is set on cell entry and fires regardless of batch progress.

If the timer fires mid-batch:
- The cell subprocess is killed
- Rows from prior completed batches in the cell are written via the streaming JSONL (preserved)
- The interrupted cell emits **K sentinel rows** (one per query position the selector planned, not K×N per planned query)

Sentinel emission matches what PR #158 cleaned up (`query_role=""` for sentinels). The sentinels mark "this cell didn't complete," not "this specific evidence value didn't complete."

### 4.4 Mid-batch exception case — atomic batch failure

If the library raises mid-batch (numerical issue with a specific evidence value, degenerate message-passing state, etc.), per §1.2's contract `query_batch` does NOT promise atomic semantics — a failure partway through MUST raise. The whole batch is the unit; all B rows get `status = "error"` (or appropriate non-ok status), same as §4.2.

### 4.5 Not_supported case — pre-batch

The existing `is_applicable` check fires before the adapter is called. If the baseline doesn't support the (problem_family, query_kind), one `not_supported` row is emitted per query position (no batching involved).

### 4.6 metrics_time_s — per-row, sequential

Scorer runs per Posterior, sequentially. `metrics_time_s` is per-row (not amortized). If we ever add a batched scorer, revisit; for now TV/JSD/W1 are per-posterior metrics.

### 4.7 Status × batching matrix

| Scenario | Status | query_time_s | batch_size | metrics_time_s |
|----------|--------|--------------|------------|----------------|
| Batch succeeds | `ok` per row | `batch_time / B` | `B` | per-row |
| Batch OOMs | `oom` per row (all B) | `NaN` | `B` | `NaN` |
| Batch raises | `error` per row (all B) | `NaN` | `B` | `NaN` |
| Cell times out mid-batch | sentinels (K rows, one per query position) | `NaN` | sentinel value | `NaN` |
| Adapter not applicable | `not_supported` (pre-batch) | `NaN` | `1` | `NaN` |

**Note on query_time_s for failed queries:**
The B=1 path preserves pre-batching behavior — failed queries
record the measured elapsed time up to the failure point (the
original single-query timing semantics). The B>1 path follows the
locked NaN convention above, since per-query timing is undefined
when the batch is atomic.
This means: at n_batch_queries=1 (existing benchmarks), failed
rows have query_time_s = elapsed-up-to-failure. At
n_batch_queries > 1, failed rows have query_time_s = NaN.
This is intentional: PR 4 (#168) preserves bitwise compatibility
with pre-batching benchmark output at the default. The §4.7 matrix
above describes the new batched path; the B=1 path uses the
original convention.

## Section 5: Speed benchmark spec (LOCKED 2026-06-07)

### 5.1 Problems

**Synthetic at n=100 across all four families. No bnlearn.**

- discrete, n=100
- continuous_lg, n=100
- continuous_nongauss, n=100
- hybrid, n=100

One problem per family (so 4 problems total). n=100 is large enough for batching to matter, small enough to OOM-proof at large batch sizes.

### 5.2 Baselines

**All applicable baselines per family.** Reference lines included; the figure shows the full picture rather than trimming.

| Family | Batchable | Non-batchable |
|---|---|---|
| discrete | nbn-cat-lw, nbn-cat-ve, nbn-neuralcat-lw, nbn-neuralcat-ve, pomegranate-discrete-ve | pyro-empirical-importance, pgmpy-mle-ve, pgmpy-bayes-ve |
| continuous_lg | nbn-lg-lw, nbn-mdn-lw, nbn-flow-lw | pyro-empirical-importance, pgmpy-lg-predict |
| continuous_nongauss | nbn-mdn-lw, nbn-flow-lw | pyro-empirical-importance |
| hybrid | nbn-hybrid-router | pyro-empirical-importance |

Applicability filtering via the existing `is_applicable` mechanism (no change).

### 5.3 `n_batch_queries`

**Top-level YAML parameter, value 10240, applied uniformly across all baselines.**

```yaml
n_batch_queries: 10240
```

The selector emits 10240 evidence-value variants per (target, evidence_vars) position for ALL baselines in the speed benchmark — including non-batchable ones. Pyro and pgmpy process them sequentially (one query at a time), nbn and pomegranate batch them per their `batch_size`.

**Implication for non-batchable baselines:** at ~10s per pyro-empirical-importance query on n=100 continuous, 10240 queries → ~28 hours per (problem, baseline, seed) cell. This is a serious feasibility concern at the speed-benchmark spec.

If the speed benchmark turns out to be infeasible for non-batchable baselines, two options at implementation time:
- (a) Accept timeouts: per-cell timeout fires, sentinel rows emitted, non-batchable curves shown as DNF
- (b) Lower `n_batch_queries` to a feasible value (e.g., 1024) — sacrifices batch-sweep granularity at the high end but completes

This is flagged as a known risk for §8. Decision deferred to PR 5 implementation when we measure actual timing.

### 5.4 `batch_sizes` sweep

**Initial sweep: `[1, 8, 32, 128, 512, 1024]`** — 6 sweep values, geometric spacing factor ~4.

Max value 1024 (not 2048) to stay conservative on memory. Can extend later if results show no plateau effect at B=1024.

### 5.5 Seeds

**5 seeds**, matching scalability benchmark convention.

### 5.6 Sweep dispatch: auto-detected

**Auto-detection rule:** any baseline whose adapter overrides `query_batch` is "swept" — runs at every `batch_sizes` value with that value as its `batch_size`. Any baseline whose adapter uses the default sequential `query_batch` is "non-swept" — runs once at `batch_size=1`.

In practice: nbn-* and pomegranate-* are swept; pyro-* and pgmpy-* are not. No YAML `swept` field needed; the property derives from whether the adapter implements the batched path.

Runner pseudo-code:

```python
for sweep_value in cfg.batch_sizes:
    for baseline in cfg.baselines:
        if baseline.adapter.has_batched_impl():
            run_cell(baseline, batch_size=sweep_value)
        elif sweep_value == cfg.batch_sizes[0]:
            # Non-swept baselines run only on first sweep iteration
            run_cell(baseline, batch_size=1)
```

**Auto-detection rule (as implemented in PR 5, #170):** each adapter declares a class-level
`supports_batched_queries: bool` flag. True on nbn and
pomegranate (their `query_batch` overrides use library-level
batching); False on pyro and pgmpy (their `query_batch` is the
sequential default helper). The sweep dispatcher checks this flag
per baseline.

**Rationale:** PR 1 (#165) gave every adapter an explicit
`query_batch` method — sequential-default adapters delegate to
`default_query_batch`, batched adapters override. So
`adapter.query_batch.__func__ is default_query_batch` (the
original §5.6 sketch) doesn't work — every adapter has its own
explicit method. An explicit class flag is unambiguous and
self-documenting.

**Pin-wins rule (§5.6 clarification):** an explicit YAML
`batch_size: N` on any baseline overrides the sweep entirely. The
baseline runs once at its pinned value, regardless of whether
`supports_batched_queries` is True or False. This resolves the
ambiguous case "a batchable baseline pinned to 1" — the pin always
wins.

### 5.7 Compute budget estimate

Cells = 4 problems × all-applicable-baselines × 5 seeds × 6 batch_sizes (for batchable) + 4 problems × non-batchable-baselines × 5 seeds × 1 (for non-batchable).

Rough per-family count:
- discrete: 5 batchable × 6 sweep + 3 non-batchable × 1 = 33 baseline-sweep cells/seed = 165 cells across 5 seeds
- continuous_lg: 3 batchable × 6 + 2 non-batchable × 1 = 20 cells/seed = 100 cells
- continuous_nongauss: 2 batchable × 6 + 1 non-batchable × 1 = 13 cells/seed = 65 cells
- hybrid: 1 batchable × 6 + 1 non-batchable × 1 = 7 cells/seed = 35 cells

**Total: ~365 cells.** With ~10240 queries each, this is a real run — not a smoke. Realistic wall-clock: hours, possibly tens of hours depending on whether non-batchable baselines complete or time out.

(Order of magnitude only — concrete timing depends on n=100 problem complexity and where the per-cell timeout lands for slow baselines.)

## Section 7: Test plan (LOCKED 2026-06-07)

### 7.1 Correctness gates (added by PR 2, PR 3)

**Per-adapter batched-vs-sequential equivalence.** For each batchable adapter (nbn, pomegranate), a unit test that:
1. Builds a small test problem (e.g., 4-node discrete network)
2. Constructs B queries sharing (target, evidence_vars), B in {1, 4, 16}
3. Runs each query via `adapter.query(q)` sequentially → list of posteriors
4. Runs all queries via `adapter.query_batch(queries)` → list of posteriors
5. Asserts pairwise equivalence within tolerance

Tolerances:
- VE (exact): `atol=1e-6` (matches existing `test_vectorized_query_batch_correctness.py`)
- LW continuous (sampling): `atol=0.05` on tv_per_node, OR statistical equivalence test (Kolmogorov-Smirnov on samples). Sampling-tolerance test is more honest.
- LW discrete (sampling): same as LW continuous

**Coverage required:**
- nbn-cat-ve, nbn-cat-lw, nbn-neuralcat-ve, nbn-neuralcat-lw on a discrete network
- nbn-lg-lw, nbn-mdn-lw, nbn-flow-lw on a continuous_lg network
- pomegranate-discrete-ve on a discrete network

The existing `test_vectorized_query_batch_correctness.py` already covers nbn-cat-ve. PR 2 ADDS coverage for the LW variants (currently missing per V1 finding).

### 7.2 Selector behavior tests (added by PR 4)

`tests/unit/test_selector_n_batch_queries.py`:

1. **n_batch_queries=1 is identity:** with the parameter at default, selector emits exactly what it does today. Compare against a baseline parquet from a pre-PR-4 smoke run.
2. **Chunking:** `n_batch_queries=10240, batch_size=512` → emits `K × 20` inner lists, each of length 512.
3. **Last-chunk handling:** `n_batch_queries=100, batch_size=64` → emits 2 inner lists of lengths {64, 36}. Last chunk smaller. Adapter should handle.
4. **Sampling with replacement:** when `n_train < n_batch_queries`, no exceptions raised, evidence values are valid (in the training distribution's support).
5. **Determinism:** same seed → same query sequence across runs.

### 7.3 Runner dispatch tests (added by PR 4)

`tests/integration/test_runner_batch_dispatch.py`:

1. **Per-query rows emitted:** a batch of B queries produces B rows in the parquet, all with `batch_size=B` and `query_time_s = batch_time/B`.
2. **Status taxonomy under batching:** force an OOM in a mock adapter, verify all B rows in the batch get `status="oom"` with `query_time_s=NaN`.
3. **Cell-level timeout under batching:** mock a slow adapter, set per_cell_timeout_s=2, verify partial-cell sentinels emit K rows (one per query position), not K×N.

### 7.4 Smoke tests (added by PR 5)

New smoke config: `nbn/bench/configs/synthetic/smoke_tests/batch_speed_smoke.yaml` — 1 problem family (discrete only), 2 baselines (nbn-cat-ve, pgmpy-mle-ve), batch_sizes=[1, 4], n_batch_queries=16, 1 seed.

Wall-clock target: < 60s on laptop CPU.

This smoke runs in CI; verifies the full pipeline (selector → adapter → runner → parquet → figure) without paper-scale compute.

### 7.5 Regression tests for existing benchmarks (verified by PR 4)

After PR 4 merges, **re-run scalability smoke and bnlearn cardinality_smoke**, compare:
- Status distribution per baseline should be identical to pre-PR-4
- `batch_size` column should be uniformly 1 in all rows
- `query_time_s` values should match pre-PR-4 within sampling tolerance

If anything regresses, PR 4 has a behavior bug that needs fixing before merge.

### 7.6 Speed benchmark integration test (added by PR 5)

`tests/integration/test_speed_benchmark_full.py`: runs the actual speed config (or a scaled-down version: n=50 instead of 100, 3 batch_sizes instead of 6, 2 seeds instead of 5) and verifies:
- All cells complete or time out cleanly
- Parquet has all expected columns including `batch_size`
- Per-baseline ok-rates are reasonable
- The amortized timing decreases monotonically with batch_size for batchable baselines

### 7.7 Paper figure test (added by PR 6)

`tests/unit/test_paper_figures_batch_speed.py`: synthesize a small test parquet with known batch_size and query_time_s distributions, render the log-log figure, verify:
- One line per baseline

## Section 8: Open questions / risks (LOCKED 2026-06-07)

### 8.1 Non-batchable baseline feasibility at n_batch_queries=10240

**Risk:** pyro-empirical-importance at ~10s/query × 10240 queries = ~28 hours/cell. May force per-cell timeouts and produce DNF rows in the speed benchmark for pyro/pgmpy.

**Mitigation deferred to PR 5 implementation:**
- (a) Accept timeouts: speed figure shows DNF annotations for non-batchable baselines on slow problems
- (b) Lower n_batch_queries: 1024 instead of 10240 (sacrifices high-batch granularity)
- (c) Add per-baseline n_batch_queries override (deferred design change if needed)

Decision deferred until PR 5 measures actual timing on n=100 problems.

### 8.2 Memory pressure at large batch sizes

**Risk:** batch_size=1024 with nbn-flow-lw on continuous_lg may OOM the GPU (especially if n_samples is also large). The §4.2 (α) decision means the cell records an oom row and the sweep continues, but if EVERY sweep value OOMs the data is unusable.

**Mitigation:** §3.5 sweep starts at batch_size=1, increases geometrically. The smallest batch size is guaranteed to work (it's what current benchmarks use). Failures happen at larger batches, and the data we have for smaller batches is still useful.

If batch_size=1 itself OOMs, the problem is too big for the speed benchmark — reduce n in the config.

### 8.3 Schema migration

**Risk:** the new `batch_size` column in `CellResult` breaks existing parquet readers that expect a fixed column set.

**Mitigation:** pandas handles missing columns on read (returns NaN). The figures pipeline needs minor updates to handle the new column gracefully. Document in PR 4.

Existing parquets (from before PR 4) don't have the column; tools should default-fill to 1 on read.

### 8.4 nbn library API stability

**Risk:** the design assumes `engine.query_batch(model, target, evidence_dict)` is the stable nbn library API. If the library refactors this surface, PR 2 breaks.

**Mitigation:** the V1 investigation pinned current behavior. If the library refactors, the test from §7.1 will catch it. Low risk because nbn is co-developed with the benchmarking framework.

### 8.5 pomegranate version compatibility

**Risk:** the design relies on pomegranate 1.1.x `predict_proba` accepting `MaskedTensor`. Older or newer versions may differ.

**Mitigation:** pin pomegranate version in `pyproject.toml`. Add a runtime version check in `pomegranate_adapter.py` __init__ that fails fast with a clear message if the version doesn't match.

### 8.6 Sweep dispatch auto-detection edge cases

**Risk:** §5.6's `has_batched_impl()` check (whether `query_batch` is the default helper vs an override) may fail for unusual adapter inheritance patterns (e.g., a mixin that calls super().query_batch()).

**Mitigation:** explicit override is the convention; document it in the adapter base class. If a future adapter has an unusual pattern, add explicit `swept: true/false` YAML field as fallback. Not needed for the initial implementation.

### 8.7 Test compute budget

**Risk:** the §7.1 correctness tests for LW continuous may have non-trivial wall-clock (sampling at multiple B values).

**Mitigation:** use small test networks (4-8 nodes), small n_samples (e.g., 200), large tolerance. Tests should run in seconds, not minutes.

### 8.8 Bnlearn relaunch timing dependency

**Risk:** Section 6 timeline implies bnlearn relaunch waits until PR 4 (schema finalized). If urgent paper-data needs arise, this may feel slow.

**Mitigation:** PR 4 is targeted at 2-3 sessions in. Bnlearn relaunch can happen as soon as PR 4 merges — possibly within a week. If urgency increases, PR 4 can be prioritized (it's the longest of the foundation PRs).

Alternatively, bnlearn could be relaunched against pre-PR-4 master, but then re-run after PR 4 ships for schema consistency. Wasted compute, but feasible.
