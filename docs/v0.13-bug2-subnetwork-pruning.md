# Bug 2: Subnetwork pruning for VE — design draft

**Status:** Design draft (pre-implementation)
**Tracker:** #127 (Bug 2)
**Related:** #109 (v0.13 roadmap), `docs/v0.13-nbn-cat-ve-investigation.md`, master commit f29084a (Bug 1a)

## 1. Background

The first paper-scale `bnlearn_paper.yaml` run crashed at barley with a 612 GB
OS-killing OOM in nbn-cat-ve. The investigation identified the root cause: nbn's
VE eliminates ALL non-target variables, not just those relevant to the query.
Querying a hub node given its full Markov blanket as evidence — which should be
trivial since the target is conditionally independent of everything else given
its MB — instead schedules 38 irrelevant variables for elimination on barley,
with intermediate factors ballooning to 612 GB.

Bug 4 (subprocess isolation, PR #129) and Bug 1a (cardinality fix, PR #130) made
the runner survive these scenarios — bad cells produce `oom` rows and the
parquet completes. But nbn-cat-ve still can't actually answer queries on
networks with dense Markov blankets. The torture smoke shows ~24 `oom` rows per
cell from allocations in the 22-109 GB range.

Standard VE has a relevant-subnetwork pruning step that nbn's VE is missing.
This design adds it.

## 2. Goals + non-goals

### Goals

- Make nbn-cat-ve tractable on dense discrete networks (barley, hailfinder,
  hepar2, andes) by pruning irrelevant variables before elimination.
- Specifically: hub-given-MB queries should be trivial (peak factor ≈ 0.001 GB).
- Preserve correctness: the pruned answer must equal the unpruned answer to
  within numerical precision.
- Implement as a separate pass that's testable in isolation.

### Non-goals (out of scope for this PR)

- Evidence absorption (slicing CPTs on evidence values rather than expanding
  them): a separate optimization in the same code area; filed as Bug 2b if needed.
- Elimination order improvement: the min-fill heuristic already exists; this PR
  doesn't change it.
- Approximate inference: VE remains exact.
- Generalizing to non-categorical mechanisms: this PR focuses on
  CategoricalTableMechanism. Other mechanisms benefit naturally if they
  participate in VE, but no special handling for continuous cases.

## 3. Approach

### 3.1 Two-technique pruning

Two classical techniques, applied together:

**Barren node elimination.** A node is "barren" with respect to
`(target, evidence)` if it has no descendants among target ∪ evidence. Barren
nodes contribute factors that integrate to 1 — they can be dropped without
affecting the answer. Cheap and always correct.

**m-separation pruning (Bayes-ball).** A node is m-separated from target given
evidence if no active path exists between them in the moralized graph.
m-separated nodes are conditionally independent of the target given the evidence
and contribute nothing. More aggressive than barren elimination — catches
conditional independences barren elimination misses.

For the hub-given-MB case: Bayes-ball alone makes it trivial (every non-MB node
is m-separated from the hub given the MB). Barren elimination is a strict subset
but cheaper to run; applying both as a combined "relevant set" check is correct
and fast.

### 3.2 Implementation: separate pass

A new module `nbn/inference/_pruning.py` exposes:

```python
def relevant_subnetwork(
    dag: nx.DiGraph,
    target: str | Iterable[str],
    evidence: dict[str, Any] | Iterable[str],
) -> set[str]:
    """Return the set of nodes relevant to inferring target given evidence.

    A node n is in the relevant set if and only if it is m-connected
    to target given evidence (Bayes-ball algorithm).

    Includes target ∪ evidence themselves. Excludes barren nodes and
    m-separated nodes.
    """
```

`TensorVariableElimination` then operates on the induced subgraph of the
relevant set. The pruning function knows nothing about factors or mechanisms —
it's pure graph algorithm on the DAG.

### 3.3 The Bayes-ball algorithm

Reference: Shachter (1998) "Bayes-Ball: The Rational Pastime",
Geiger-Verma-Pearl (1990).

Single-pass traversal. Maintains a queue of (node, direction) pairs where
direction is one of:

- "from_child" — ball arrived from a child (or this is the initial target
  inquiry)
- "from_parent" — ball arrived from a parent

Each node carries up to two marks: "top" (reached from a child) and "bottom"
(reached from a parent). The marks serve as termination guards — a node is
expanded at most once per direction.

Rules for processing (node, direction):

- **from_child, non-evidence**: mark top + bottom; propagate up to parents
  (still "from_child") AND down to children ("from_parent")
- **from_child, evidence**: ball is BLOCKED. A chain or fork through an observed
  node is inactive.
- **from_parent, non-evidence**: mark bottom only; propagate down to children
  ("from_parent")
- **from_parent, evidence**: ball BOUNCES UP. Mark top; propagate up to parents
  ("from_child"). This is the v-structure (collider) activation rule:
  conditioning on a collider makes its parents m-connected. Also handles
  descendant-evidence: a ball travelling down hits an observed descendant of a
  collider, bounces back up, and reaches the collider's other parent.

Initialization: for each node t in target, enqueue (t, "from_child"). This
represents inquiring about t.

The **relevant set is the top-marked nodes** (those reached from a child) plus
target and evidence themselves. Bottom-only nodes are barren — their factors
integrate to 1 and contribute nothing to the answer. This is what makes "query
target with no evidence" correctly exclude all descendants of the target.

Time complexity: O(V + E). Implementation ~100 lines including the
direction-aware edge traversal.

A concrete reference implementation exists in pgmpy and daft. We implement from
scratch to keep nbn dependency-free of pgmpy at the inference layer.

### 3.4 Integration with TensorVariableElimination

In `nbn/inference/tensor_ve.py`:

Before computing the elimination order, restrict the working set:

```python
# Existing code:
all_vars = list(self.model.dag.nodes())
to_eliminate = [v for v in all_vars
                if v not in target_set and v not in evidence]

# New code:
relevant = relevant_subnetwork(self.model.dag, target, evidence)
to_eliminate = [v for v in relevant
                if v not in target_set and v not in evidence]
```

The min-fill elimination order is then computed on the relevant subgraph instead
of the full graph. Mechanisms for non-relevant variables are simply not
consulted.

### 3.5 Correctness guarantee

Pruning is a strict improvement: the pruned answer equals the unpruned answer
exactly (to numerical precision). This is the mathematical guarantee of
m-separation. We verify empirically by comparing pruned results against unpruned
results on a held-out test problem (see §6).

## 6. Testing strategy

### 6.1 Unit tests (Stage 1)

`tests/unit/v013/test_pruning.py`:

- `test_target_only`: query with no evidence returns ancestors of target
- `test_barren_nodes_excluded`: target = leaf, all descendants of leaf siblings
  should be barren
- `test_evidence_separates`: known DAG where evidence m-separates target from a
  third node
- `test_v_structure_unblocked`: collider with evidence on the collider or its
  descendant makes the parents m-connected
- `test_v_structure_blocked`: same collider without evidence keeps parents
  m-separated
- `test_hub_given_mb`: barley-like structure, hub target + full MB evidence
  returns just the MB + hub (no other nodes)
- `test_full_evidence`: every non-target node observed → relevant set is target
  + evidence (no other nodes can contribute)
- `test_no_evidence`: same as target_only but explicit empty dict
- `test_chains`: linear chain with evidence in the middle blocks both directions

### 6.2 Integration test (Stage 2)

- A small problem (asia or sachs) with a specific query — verify that pre-fix
  and post-fix produce identical posteriors to within numerical precision (1e-6).

### 6.3 Torture smoke (Stage 3)

- Re-run `benchmarking/configs/bug4_torture_smoke.yaml`
- Expected change: oom rows (currently 24 per cell from 22-109 GB attempts)
  should drop to ~0
- ok rows should increase correspondingly
- Total row count (666) should be unchanged

### 6.4 Scalability check (Stage 4)

A small benchmark script comparing query time on:

- asia (8 nodes, no pruning effect expected)
- barley (48 nodes, dramatic pruning effect expected)
- hailfinder (56 nodes), hepar2 (70 nodes): expected significant speedup on hub
  queries

Specifically measure:

- Pruning function overhead in absolute milliseconds (should be < 1ms even on
  the largest network)
- Query time pre/post fix ratio (1× on asia, 1000×+ on barley hub queries)

Results captured in the Stage 4 commit message.

## 7. Risk assessment

### Likely concerns

**Subtle Bayes-ball bugs.** The algorithm has direction-aware edge traversal —
easy to get wrong. Mitigation: extensive unit tests covering the standard cases
(chains, forks, colliders, v-structures), plus an integration test verifying
numerical equality with the unpruned result.

**Performance on small networks.** Pruning adds overhead. Mitigation: on small
networks the function returns quickly (most nodes are m-connected anyway), and
the absolute overhead (< 1ms) is dwarfed by factor allocation time. Verified in
Stage 4.

**Interaction with other v0.13 work.** Bug 1a fixed cardinality handling but
pruning operates on the DAG structure, not the CPTs. The two fixes are
orthogonal.

### Unlikely concerns

**Disconnecting target from evidence.** If pruning erroneously m-separates
target from evidence that's actually conditionally relevant, the answer is
wrong. Mitigation: the Bayes-ball algorithm is mathematically proven correct; we
don't reinvent it.
