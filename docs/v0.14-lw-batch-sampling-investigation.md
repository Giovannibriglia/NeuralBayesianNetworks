# LW batched-sampling investigation (issue #180)

**Date:** 2026-06-09  **HEAD:** `11fdb70` (post-PR #176 fit-once, post-PR #179 guard)
**Scope:** investigation only, no code changes. Advisory for the implement-now /
design-doc-first / document-and-move-on decision.

## TL;DR — the issue's implementation hypothesis is wrong

Issue #180 hypothesizes that LW `query_batch` "doesn't actually batch the
sampling work" and proposes "draw `B×N` samples once and reuse the sample
matrix." **The code already draws `B×S` samples in a single vectorized GPU
launch per node — there is no per-query Python loop.** The near-linear
`batch_time` growth is *genuine compute* (B× more particles to push through
every mechanism), not sequential dispatch. The naive "batch the sampling" fix
is already implemented. The only remaining sampling-sharing opportunity is
**structure-dependent and algorithmic**, not a clean implementation win.

## LW engine location

- Class: `nbn/inference/likelihood_weighting.py:12` `LikelihoodWeightingEngine`
- Core IS loop: `_run()` `likelihood_weighting.py:34-107`
- `query()`: `likelihood_weighting.py:109-151`
- `query_batch()`: `likelihood_weighting.py:153-161` — *just delegates to
  `query()`*; the batch dim is carried by the evidence tensors, not by a loop.
- Adapter dispatch: `benchmarking/adapters/nbn_adapter.py:342` stacks evidence
  into `[B, D]` and makes one engine call.
- Mechanism sampling (cat): `nbn/mechanisms/categorical_table.py:221` `sample()`
  — `Categorical(logits=logits_flat).sample()` over `[B*n, K]`, fully vectorized.

## Current loop structure (what's sampled, what's weighted)

`_run` allocates `buf [B, S, total_dim]` and `log_w [B, S]`
(`likelihood_weighting.py:64-65`) and walks the topo order **once**
(`:74`). For each node, in a single GPU launch over all `B*S` particles:

- **Evidence / do nodes** (`:85-97`): clamped to per-query value
  `fixed[i] = v.unsqueeze(1).expand(b, s, -1)` (`:72`). Evidence nodes also add
  `mech.log_prob(obs, pa)` to `log_w` (`:93-94`) — **the weighting step**.
- **Non-evidence nodes** (`:98-105`): sampled from the conditional given parents
  via `mech.sample(pa_flat, n=1)` where `pa_flat = pa.reshape(b*s, -1)` — **the
  sampling step**.

Only one Python iteration per *node*; the `B` and `S` axes are flattened into
the tensor and never looped. The `for ci in range(k)` at `:141-143` loops over
target *classes* (small), not queries.

## Vectorization opportunity — already taken, plus a structural caveat

**Already vectorized across queries:** all sampling and all weighting. Each
node's `sample`/`log_prob` runs once on a `[B*S, ...]` tensor. So "batch the
sampling" in the sense issue #180 imagines is done.

**Why batch_time still scales ~linearly in B:** the work is genuinely `B×S`
particles. With the adapter's `n_samples=1024` and B=1024 that is ~1M particles
× ~100 nodes ≈ 1e8 mechanism evals. Once the device saturates (and on the
CPU-bound laptop probe, immediately), time is linear in the particle count. VE
scales sub-linearly because it broadcasts a *fixed-size* factor table over the
batch axis — the batch doesn't multiply per-element work the way particles do.

**The one real sharing opportunity — and why it's not clean:**
LW samples non-evidence nodes conditioned on their parents, and parents include
*clamped evidence values* (`pa` reads from `buf`, which holds the per-query
`fixed[i]`, `:81-82` + `:100-105`). Therefore:

- A non-evidence node that is **a descendant of some evidence node** is sampled
  conditioned on the per-query evidence value `e`. Its `S` samples genuinely
  differ across the `B` queries → **cannot be shared** (algorithmic, not
  implementation; confirmed by code).
- A non-evidence node that is **not a descendant of any evidence node** has
  evidence-independent samples → could be drawn once as `[S, D]` and broadcast,
  instead of `[B, S, D]`. This is the only `B×`-reducible sampling.

So the achievable gain depends entirely on graph topology (how much of the
network sits *upstream/independent* of the evidence set).

## Implementation options

**Option A — partition nodes by evidence-reachability, sample shared nodes once.**
- Where: `_run` (`likelihood_weighting.py:74-105`), plus a per-(model, evidence
  set) precompute in `state.py` marking "descendant-of-any-evidence".
- For non-descendant nodes draw `[S, D]` once; broadcast into `buf`'s `[B,S,D]`
  slice. Descendant nodes keep the `[B*S]` path.
- LOC: ~40–70 (reachability tag in `InferenceState`, a branch in the node loop,
  buffer broadcasting). Cacheable per query signature (cache already keyed on
  evidence keys).
- Subtleties: weights still per-query; mixing shared `[S]` and per-query `[B,S]`
  tensors in `buf` needs careful `expand` (no accidental aliasing on write).
  Gain is zero when all nodes are downstream of evidence.

**Option B — share one `[S, D]` sample set across all queries (issue's idea).**
- Statistically *invalid in general*: it forces descendant nodes to ignore the
  per-query evidence parent, changing the importance distribution. Only correct
  when evidence nodes have no descendants (all-leaf evidence). Not recommended
  as a default; would need a graph guard + opt-in.

**Option C — accept current behavior.**
- The engine is already optimally vectorized for the general case. The 1.6–1.8×
  speedup is real (setup/Python amortization) and correctly documented. No code
  change; close #180 as "works as designed; partial structural optimization
  tracked separately."

## Expected gain (order of magnitude)

Sampling dominates weighting here: in the discrete n=100 problem only a handful
of nodes are evidence (weighted) while ~all others are sampled, so sampling is
~70–90% of per-query work. **Ceiling** for Option A is therefore high *only if*
most nodes are evidence-independent. But query selectors put evidence to
*condition* targets, and conditioning is informative precisely when evidence has
descendants — so in realistic queries a large fraction of nodes are downstream
of evidence and **not** shareable. Realistic expected gain: modest (well under
the issue's hoped 3–10×) and highly graph-dependent; could be ~0 for
evidence-at-roots topologies.

## Recommendation

**Path B (design-doc-first), leaning toward Option C / narrow Option A.**

The issue's framing ("sampling isn't batched") is empirically true at the
`batch_time` level but mechanistically inaccurate: sampling *is* batched; the
cost is intrinsic `B×S` particle compute. There is no quick implementation win.
The only correct optimization (Option A: share evidence-independent node
samples) is graph-topology-dependent and likely modest for the queries the
benchmark actually runs. Recommend:

1. Correct issue #180's "Proposed fix scope" with this finding (sampling already
   vectorized; remaining win is structural + bounded).
2. Decide Option A only if a quick topology audit of the benchmark DAGs shows a
   meaningful evidence-independent fraction. Otherwise document and close.

## Test plan implication (for any eventual Option A implementation)

Per the PR #179 "this still works" + "this actually helps" pattern:

1. **Correctness / statistical equivalence:** on a small known-answer discrete
   net, assert batched-with-shared-sampling posteriors match the current
   `_run` posteriors within Monte Carlo tolerance (e.g. fixed seed, same total
   particle count, `torch.allclose(probs_new, probs_old, atol≈3·SE)`), and match
   an exact VE reference on the same net. Critically include a DAG where evidence
   *has* descendants to prove those nodes are still sampled per-query.
2. **Performance:** assert `batch_time(B≥64)` strictly below the current
   implementation on a DAG with a large evidence-independent subgraph; record
   that the gain is ~0 (and that this is expected) on an evidence-at-roots DAG so
   the bound is documented, not silently hidden.
