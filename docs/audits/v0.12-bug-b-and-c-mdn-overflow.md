# v0.12 Bug B + Bug C resolution — MDN overflow at deep continuous_nongauss chains (PRs #90, #93)

Tracking issues: [#81](https://github.com/Giovannibriglia/NeuralBayesianNetworks/issues/81) (Bug B),
[#24](https://github.com/Giovannibriglia/NeuralBayesianNetworks/issues/24)
(NaN origin in deep continuous_nongauss chains),
[#54](https://github.com/Giovannibriglia/NeuralBayesianNetworks/issues/54)
(MDN gradient stability). Master at audit time: `9fcd2ee`. Fix landed:
PR [#90](https://github.com/Giovannibriglia/NeuralBayesianNetworks/pull/90)
(merged 2026-05-18, two commits on
`fix/v0.12-mdn-parent-standardization-bug-B`).

## TL;DR

Bug B — the NaN-driven `MultinomialKernel` CUDA assert that prevented
`nbn-mdn-lw` and `nbn-flow-lw` from running on `continuous_nongauss` —
is fixed by per-node parent standardization inside `MDNMechanism`. The
fix is applied **inside the mechanism**, not inside the synthetic-data
generator: the upstream root cause (deep ancestral chains producing
3.3M-scale parent values at paper-config scales) is a real property of
the benchmark family, and the MDN must be numerically robust to it
rather than relying on the data generator to bound the range.

The fix is two commits. Commit 1 adds parent standardization with
`pa_mean` / `pa_std` `register_buffer`s computed in `fit_local` and
applied in `_params_from_parents`. Commit 2 removes a
double-standardization bug caught during the Phase 5 edge-case audit
(pre-standardizing in `fit_local` combined with the per-call
standardization in `_params_from_parents` produced training/inference
inconsistency and a constant-parent NaN crash). The
`_sanitise_parents` band-aid from v0.6c-A Finding 2 stays in place as
defense in depth.

## Scope

  the overflow path never triggered).

## Failure path (Phase 1 + Phase 2 findings)

Phase 1 training-data inspection on `continuous_nongauss n=50 seed=3`
showed extreme parent values from deep ancestral chains:

| Node | abs_max(parent value) | Chain depth |
|---|---:|---:|
| X21 | 3.3 × 10⁶ | 5 hops |
| X42 | 5.6 × 10⁵ | 4 hops |

Phase 2 per-step instrumentation in `MDN.fit_local` localised the
failure to epoch 0 step 2, with the following sequence:

1. `parents` batch contains a row with one component ≈ 3.3 × 10⁶.
2. `_params_from_parents` computes
   `out = self.net(parents)`; the final linear layer's row mapping to
   the `log_scale` slot has a non-trivial weight, so
   `log_scale ≈ 3.3e6 × w ≈ O(10⁵)` after the MLP forward pass.
3. `scale = torch.exp(log_scale).clamp_min(self.min_scale)` overflows
   to `+inf` (`exp(O(10⁵))` exceeds float32 range).
4. `Normal(loc, scale=inf).log_prob(x)` evaluates to `-inf` for the
   in-batch rows and produces a loss of magnitude ≈ 1.87 × 10¹⁴.
5. `loss.backward()` overflows the gradient buffers to NaN.
6. The Adam step writes NaN into the MLP weights and biases.
7. From epoch 0 step 3 onward, every forward pass produces NaN
   parameters. Training "completes" but the model is unusable.
8. At LW inference, `_params_from_parents` returns NaN logits;
   `Categorical(probs=softmax(NaN))` produces an invalid probability
   tensor; the CUDA `MultinomialKernel` launches a sampling assert and
   fires `cudaErrorAssert`, reported asynchronously.

The visible symptom in the paper-run parquet — "CUDA error:
device-side assert triggered" — is step 8. Steps 1–7 happen silently
during fit.

The pre-existing `_sanitise_parents` guard at `mdn.py:16-59` (added
in v0.6c-A Finding 2) replaces non-finite parent values with 0, but
**the parents at this scale are finite — they are just extreme** —
so the sanitiser passes them through unmodified. Bug B is therefore
distinct from the v0.6c-A finding that motivated the sanitiser;
they share the visible CUDA-assert symptom but differ in the parent
state that triggers it.

## Fix design

Per-node parent standardization, computed once in `fit_local` from
training data and applied at every forward call in
`_params_from_parents`.

### Why parents-only, not also `x`

The MDN's outputs (`logits`, `loc`, `log_scale`) are predicted by an
MLP from `parents` only. Extreme `x` values do not flow through the
network and can't drive overflow. Standardizing `x` would shift the
predicted `loc` and `scale` parameters relative to the data, making
log-prob comparisons against pre-fix runs incomparable — for no
numerical benefit. Parents-only standardization keeps the predicted
density in the same coordinate frame as the training data.

### Why per-node, not per-family

Standardization statistics are properties of the per-node parent
distribution. Sharing statistics across nodes would couple unrelated
CPDs and break the structural assumption that each
`MDNMechanism` is a standalone CPD. Per-node also keeps the fix
local — no changes to the model class or the runner needed.

### Why `register_buffer`, not `nn.Parameter` or plain attributes

`register_buffer` ensures the statistics survive `state_dict()` save
and load — necessary for the v0.7 fit-then-query semantics
(PR #28) where the *fitted* model is queried at inference time, not
the truth model. The Phase 6 state_dict round-trip test verifies
this: fit a model, save, reload into a fresh instance, compare
forward pass outputs against the original — `max_diff = 0.00e+00`.

Buffers (not parameters) because the statistics are computed from
data, not learned by gradient descent.

### Single canonical standardization path

The Phase 5 edge-case audit caught a double-standardization bug in
commit 1's initial form: `fit_local` pre-standardized parents before
the training loop, and `_params_from_parents` also standardized at
every forward call. This produced:

- **Training/inference inconsistency at large-scale parents**: during
  fit the network saw `(parents − mean) / std` pre-standardized; at
  inference it saw `((parents − mean) / std − mean) / std`, which is
  a different input distribution.
- **Constant-parent NaN crash**: for a parent column with
  `std = 0`, `pa_std.clamp_min(1e-3)` saved the first standardization,
  but the second standardization at inference time saw inputs of
  exactly 0 (the standardized constant), then re-standardized to
  `(0 − 0)/1e-3 = 0`, which is fine — but during training the
  pre-standardized `0` then went through the MLP, and the second
  standardization inside the same call computed
  `(0 − mean=0) / std=1e-3 = 0` repeatedly, causing the network to
  see only zeros and produce undefined gradients.

Commit 2 removed the pre-standardization in `fit_local`.
`_params_from_parents` is now the **single canonical standardization
path**, applied identically at train and inference. This is the
invariant the Phase 5 audit re-checks for every edge case.

## Bug C: inference-time MDN overflow at deep continuous_nongauss chains (PR #93)

### Discovery context

Discovered during PR #90 validation: a targeted `continuous_nongauss`
re-run produced `ok` rows for `nbn-mdn-lw` at n=10/50 seed=0, but
errored at n=100 seeds 1–4 and at n=500/1000. Initial hypothesis was
gpytorch CUDA context contamination; isolated reproduction at
n=100 seed=1 `nbn-mdn-lw` confirmed Bug C is real and distinct from
Bug B.

The key distinction: Bug B was a **training-time** failure — extreme
parent values during `fit_local` caused gradient overflow and NaN
parameters, which then crashed at inference. Bug C is a
**inference-time** failure — the *fitted* model has healthy parameters
(Bug B fixed), but the LW sampler's ancestral sampling chain produces
extreme particles at inference time that then overflow the fitted MLP.

### Failure path

1. LW draws B×S particles (B=1024 evidence rows × S=4000 samples =
   4,096,000 particles per node) for inference.
2. Deep `continuous_nongauss` chain produces extreme but finite
   particle values: e.g. raw parent ≈ 1362, pa_std ≈ 0.56 → **731σ**
   after standardization.
3. MLP forward on 731σ input → `log_scale` output is large.
4. `exp(log_scale) = Inf` → `scale = Inf`.
5. `sample = loc + Inf × randn = Inf` — stored in the LW buffer.
6. Downstream nodes receive the Inf particle as parent input.
7. `_sanitise_parents` zeros the Inf to 0 (warning fires), but some
   path produces NaN logits from the combined MLP inputs.
8. `softmax(NaN logits)` = NaN → `Categorical(probs=NaN)` → Simplex
   constraint violation → CUDA assert.

### Measurement evidence (Phase 1 investigation)

**Measurement 1 — pa_std distribution** (fitted model, n=100 seed=1):

The prior hypothesis that "pa_std ≈ 1e-3" was incorrect. pa_std after
PR #90 is healthy across all MDN nodes:

| Statistic | Value |
|---|---|
| pa_std overall min | 0.40 |
| pa_std median | 0.55 |
| pa_std max | 1.86 |
| Dims at 1e-3 clamp | 0 / 93 non-root nodes |

The 1e-3 clamp is never hit. Bug C is driven by extreme
**inference-time** particles, not by degenerate pa_std.

**Measurement 2 — overflow trace** (B=1024 × S=4000, 3 trials):

Overflow events were reliably triggered (pre-clamp standardized values
>50σ on every trial) and trial 3 crashed with the Simplex constraint
violation. Pre-clamp magnitudes observed:

| Validation cell | Max pre-clamp σ | Clamped rows |
|---|---:|---:|
| n=100 seed=1 | 28.9 M | 9,854 |
| n=100 seed=2 | 280 | 16 |
| n=100 seed=3 | 375.9 M | 12,415 |
| n=100 seed=4 | 239 k | 214 |
| n=500 seed=0 | 1.28 M | 1,144 |
| n=50 seed=3 (Bug B canonical) | **7.2 B** | 309 |

The Bug B canonical cell (n=50 seed=3) showed 7.2 billion σ inference
inputs even after Bug B's training-time fix. PR #90 prevented the NaN
parameters; it did not prevent the LW sampler from producing
pathological particles — those were reaching the fitted MLP silently
and producing unpredictable outputs.

### Fix (PR #93)

Add `self._pa_clamp: float = 50.0` to `MDNMechanism.__init__`. In
`_params_from_parents`, after standardization, clamp:

```python
parents = parents.clamp(-self._pa_clamp, self._pa_clamp)
```

50σ is already wildly OOD relative to training data — predictions at
that distance are noise regardless of threshold. The threshold ensures
`exp(log_scale × W)` stays finite for any learned weight `W < 1.76`,
a comfortable margin given weights after 20 training epochs on O(1)
inputs are O(0.1–1.0). `_pa_clamp` is a class attribute (tunable)
rather than a hard-coded literal.

### Validation (Phase 3B, 2026-05-18)

7-cell matrix, 3–5 trials each, CPU, `CUDA_LAUNCH_BLOCKING=1`:

| Cell | Result | Clamp fired | Max pre-clamp |
|---|---|---|---|
| `continuous_nongauss` n=100 seed=1 | ✅ PASS | Yes | 28.9 M σ |
| `continuous_nongauss` n=100 seed=2 | ✅ PASS | Yes | 280 σ |
| `continuous_nongauss` n=100 seed=3 | ✅ PASS | Yes | 375.9 M σ |
| `continuous_nongauss` n=100 seed=4 | ✅ PASS | Yes | 239 k σ |
| `continuous_nongauss` n=500 seed=0 | ✅ PASS | Yes | 1.28 M σ |

Clamp fires on every `continuous_nongauss` cell (load-bearing) and is

Regression test added: `test_mdn_extreme_inference_parents_no_nan_bug_c`
in `tests/unit/test_mdn_robustness.py`. Fits an MDN on clean data,
injects 1000σ parents, asserts both `sample()` and `log_prob()` return
finite values. Full unit suite: 12/12 pass.

## Addendum: gpytorch-gp-predict architectural limitation (2026-05-20, issue #96)

### Background

During the Bug C follow-up investigation, the gpytorch baseline was examined because its `total_time_s ≈ 1s` across all sizes (n=10 through n=1000) raised a timing anomaly flag (issue #96). The expectation was that GP regression — being O(n³) for exact inference — should scale visibly with graph size. The observed flat timing prompted instrumentation to characterize what work the adapter was actually performing.

### Finding: per-node SVGP cannot do BN inference

The gpytorch adapter is structured as follows:

- **Fit phase**: trains one SVGP (Stochastic Variational GP, 64 inducing points, 40 Adam steps) per non-root node, modeling `P(node | direct_parents)`. Each SVGP sees only its node's value and its direct parents' values across the training data.
- **Query phase**: for each query `P(target | evidence)`, evaluates the target's SVGP at evidence-derived parent inputs. Specifically, the adapter calls `q.evidence.get(parent, 0.0)` to retrieve each direct parent's value from the evidence dict.

The architectural issue is in the query phase. The benchmark's evidence is selected from **descendants and laterals of the target**, never from the target's direct parents. For example, in a 100-node BN, a query might predict node X15 (whose parents are X1, X2, X7, X10) given evidence on X59, X71, X57 — all non-ancestors. The adapter cannot route information from non-ancestral evidence to the target's parents because there is no inter-SVGP message passing.

As a result, `q.evidence.get(parent, 0.0)` returns the default 0.0 for every parent in every query, and each target prediction is the conditional mean at the prior parent value (zero), independent of the evidence values. The agent's instrumentation at continuous_nongauss n=100 seed=0 confirmed:

- Target X15's parents: [X1, X2, X7, X10]
- Evidence: [X59, X71, X57]
- Parents in evidence: 0 / 4
- Prediction std across queries: ~0.05 (essentially constant)

This is not a code bug. The adapter is correctly implementing what it sets out to do — per-node GP regression with naive input substitution. The mismatch is between that operation and what BN inference requires.

### Fit-time vs query-time split

The `total_time_s` metric reported in the parquet measures only the query phase. The fit phase is excluded from the cell timing budget. Instrumentation produced the following decomposition for continuous_nongauss:

| n_nodes | Fit time (excluded from total_time_s) | Query time (= total_time_s) |
|---:|---:|---:|
| 10 | ~10 s | ~0.04 s |
| 100 | ~96 s | ~0.04 s |
| 500 | ~480 s | ~0.92 s |
| 1000 | ~960 s | ~1.01 s |

Two consequences:

1. **The reported timing column understates gpytorch's true cost.** At n=100, the parquet records 0.99s; the actual end-to-end cost (fit + query) is approximately 97s. For NBN-MDN-LW the parquet's `total_time_s` is closer to a full accounting (the LW sampling dominates and is what the metric measures).

2. **This explains the continuous_lg timeouts at n ≥ 500.** The per-cell budget is 1200s. At n=500, fit alone is ~480s; at n=1000, ~960s. Combined with the overhead of inference and metric computation, cells at n≥500 approach or exceed the budget for continuous_lg. The continuous_nongauss cells completed because their fit appears to converge faster (smaller signal magnitudes in the standardized SVGP inputs after training), but the same cliff appears at n=1000.

### Implications for paper §5 comparison

`accuracy_supported=False` for gpytorch-gp-predict is architecturally necessary, not a flag to flip. Distributional metrics (accuracy, JSD, TV, W1) compare a baseline's outputs against true conditionals; gpytorch-gp-predict's outputs are noise-floor predictions at parent=0, not Bayesian-inference outputs. The metrics would not produce meaningful comparisons even if computed.

This leaves the paper with three honest framings for §5:

- **Include gpytorch in the headline comparison with explicit disclaimers.** Report timing only (with a footnote distinguishing fit-time and query-time), mark distributional metrics as inapplicable. Pros: visibility for a recognized third-party framework. Cons: invites confusion about why gpytorch's "timing" is much smaller than NBN's at all scales.

- **Demote gpytorch to a separate fit-time scalability subsection.** Compare gpytorch's fit-time scaling to NBN's full-pipeline scaling. This is the comparison where gpytorch genuinely does something analogous (both methods fit per-node mechanisms; the costs are real and comparable). Pros: fair comparison at a meaningful task. Cons: changes the paper's experimental design.

- **Exclude gpytorch from §5 entirely.** Reference in related work as a Bayesian-ML framework with GP-based modeling, but not included in the inference benchmark because the adapter does not perform BN inference. Pros: cleanest framing; no asterisks. Cons: paper has no third-party baseline on continuous_nongauss inference.

The paper authors should decide based on what contribution claim is being made. If the claim is "NBN provides a unified BN inference framework that handles continuous_nongauss where existing tools cannot," exclusion or demotion both support that. If the claim is "NBN is competitive with established frameworks," there is no current way to support that on continuous_nongauss because no established framework does this task as defined.

### Open question

Fixing the accuracy gap would require building a proper inference algorithm on top of the per-node SVGPs — either Likelihood Weighting over the GP posteriors (treating each GP's predictive distribution as a generative model and propagating samples through ancestral order) or message-passing where conjugacy permits. This is a multi-day engineering project, not a small adapter fix. Discrete/hybrid family extension (via gpytorch's BernoulliLikelihood, SoftmaxLikelihood, or VariationalGP) inherits the same architectural limitation: each per-node GP-classifier would still face evidence on non-parent nodes.

Tracked in issue #96 as a candidate v0.8 architectural investigation, not paper-blocking.
