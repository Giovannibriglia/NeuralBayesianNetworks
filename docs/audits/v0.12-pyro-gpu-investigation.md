# v0.12 pyro GPU investigation

**Date:** 2026-05-21
**Status:** Resolved — pyro hardcoded to CPU via YAML `device: cpu` override.
**PR:** #102
**Related issues:** —

## Background

During v0.12 paper data collection, we investigated whether moving the
pyro adapter from CPU to GPU would speed up the targeted pyro re-run.
pyro's documentation describes GPU support via CUDA tensor placement; the
pyro adapter in our codebase was forcing CPU via explicit `.cpu()` calls
on all input tensors.

**Hypothesis:** removing the `.cpu()` forcing and plumbing `device` through
the adapter would let CUDA-capable users benefit from GPU acceleration on
continuous and hybrid families.

## Implementation (feat/v0.12-pyro-device-support branch)

- `PyroAdapter` accepts a `device` constructor parameter (default `"cpu"`
  for backward compatibility; supports `"cuda"` and `"auto"`).
- All training-data tensor reads replaced `.cpu()` with `.to(self.device)`.
- All `torch.zeros`/tensor constructors specify `device=self.device`.
- Output tensors moved back to CPU at the adapter boundary (matches the
  contract of other adapters).
- `"auto"` resolution: if `device == "auto"`, resolve to `"cuda"` if
  `torch.cuda.is_available()` else `"cpu"` at construction time.
- `lstsq` driver: `gelsd` is CPU-only in PyTorch; on CUDA the adapter
  uses `driver="gels"` (full-rank QR). This is a PyTorch constraint,
  not pyro-specific.

## Empirical findings

Validation cell timings, `continuous_lg n=50 seed=0`, `pyro-empirical`:

| Device | Timing metric (s) | Speedup vs CPU |
|--------|------------------:|---------------:|
| CPU    | ~75               | 1.0×           |
| CUDA   | 860               | **0.09× (11× slower)** |

Accuracy values matched between CPU and CUDA implementations (no
numerical divergence). The slowdown is purely a performance issue,
not a correctness one.

Phase 3 validation (n=10, all applicable families × both variants):

| Family | Metric | GPU value | CPU reference |
|--------|--------|-----------|---------------|
| discrete | tv_per_node | 0.144 | 0.14–0.16 |
| continuous_lg | w1_per_node | 0.086 | ~0.12 |

All 6 cells (discrete/continuous_lg/hybrid × empirical/importance) passed
without CUDA errors after fixing the `gelsd`→`gels` driver issue.

## Root cause

`pyro.infer.Importance` runs the model function N times in a Python loop.
Each iteration executes the BN ancestrally, calling
`pyro.sample(name, dist.Normal(mu, sigma))` (or `dist.Categorical`) per
node. Each `pyro.sample` produces a scalar tensor.

On CPU these tiny tensor operations dispatch directly to the CPU arithmetic
backend with negligible overhead. On CUDA, every `pyro.sample` triggers a
CUDA kernel launch (~5–10 μs overhead per launch). The compute itself is
so cheap that the kernel launch overhead dominates. At benchmark scale
(n_samples=50 particles × B=1024 queries × up to 50 nodes per cell), the
cumulative kernel launch overhead overwhelms any compute speedup.

This is consistent with pyro's own JMLR paper (Bingham et al., 2019),
which notes that GPU benefits scale with tensor-op size; pyro's Importance
sampler has many small ops, not few large ones.

## Decision

pyro stays on CPU in the benchmark, enforced via the YAML `device` override
field introduced in PR #102:

```yaml
- {library: pyro, mechanism: empirical, param_method: mle,
   inference_method: importance, device: cpu}
```

The `device` field is optional; when absent, a baseline inherits
`cfg.device`. The pyro adapter's `device` parameter infrastructure is
preserved — validated as working and potentially useful for callers with
different workloads (e.g., large-batch SVI on GPU).

## What we did not do

**Vectorise via `pyro.plate`.** This would batch the N particles into a
single tensor operation, amortising CUDA kernel launch overhead. Estimated
1–2 weeks of engineering; not done because the CPU path is fast enough and
produces correct paper data.

**SVI or NUTS inference paths.** These are pyro's GPU-friendly inference
modes but require parameterised guides — different fit-paths from
Importance, larger scope change. Tracked as a potential v0.8+ improvement
if pyro's role in the benchmark grows.
