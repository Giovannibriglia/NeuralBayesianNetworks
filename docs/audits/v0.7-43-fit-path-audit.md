# v0.7-#43 fit-path audit

Tracking issue: [#43](https://github.com/Giovannibriglia/NeuralBayesianNetworks/issues/43).
Master at audit time: `8ab7066`. Paper-data anchor: tag `v0.6c-d` at commit
`2e0dd32`. Branch where audit + companion fix land: `feat/v0.7-adapter-cleanup`.

## TL;DR

The original #43 finding — that `pgmpy-mle` ≡ `pgmpy-bayes` and `nbn-cat` ≡
`nbn-neuralcat` produce bit-identical `tv_per_node` rows in the v0.6c-d
parameter-learning parquet — is a **runner-side bug** (Diagnosis B), not
honest-convergence (Diagnosis A) and not an evaluation conflation
(Diagnosis C).

Both pairs collide at `_param_learning_cell` (`benchmarking/crash_test_runner.py:300-308`),
which dispatches on the **legacy adapter string** (`"nbn"` / `"pgmpy"`) rather
than the method-keyed label, then `run_parameter_learning` (line 200-201)
relabels result rows back to the method-keyed name. The parquet shows
method-keyed columns, but the underlying fit is shared per family. Bit-identical
TV is the natural runtime symptom.

The paper's headline parameter-learning finding — "NBN-cat 2.3× more accurate
than pgmpy-mle on discrete at scale" — compares two **genuinely distinct** fit
paths and is unaffected. The bug only affects duplicate-pair rows
(`nbn-neuralcat`, `pgmpy-bayes`) in the parameter-learning parquet, which
silently mirror their `nbn-cat` / `pgmpy-mle` siblings.

## Scope

This audit is **doc-only**. The runtime fix is queued for v0.8 across three
focused issues:

- [#51](https://github.com/Giovannibriglia/NeuralBayesianNetworks/issues/51) — runner: dispatch on the method-keyed spec, not the legacy string.
- [#52](https://github.com/Giovannibriglia/NeuralBayesianNetworks/issues/52) — `NeuralCategoricalMechanism` root-node never trains (latent bug surfaced during this audit; independent of the runner fix).
- [#53](https://github.com/Giovannibriglia/NeuralBayesianNetworks/issues/53) — `_fit_and_score_pgmpy` doesn't plumb `param_method`.

The v0.6c-d parquets, run.jsons, tables, and figures are untouched. The
`docs/v0.6c-d/run_summary.md` gets a one-paragraph audit caveat pointing to
this document. Future runs (after the v0.8 fix lands) will diverge from
v0.6c-d on the duplicate-pair rows; they will agree on `nbn-cat` and
`pgmpy-mle` rows, which are the paper's headline.

## Verification path (read-only)

### 1. Adapter classes are architecturally distinct

`pgmpy-mle` and `pgmpy-bayes` route through the same `PgmpyAdapter` class but
distinct branches at `benchmarking/baselines/pgmpy_adapter.py:82-96`:

```python
if self.param_method == "bayes":
    from pgmpy.estimators import BayesianEstimator
    bn.fit(
        df, estimator=BayesianEstimator,
        prior_type="BDeu", equivalent_sample_size=5,
    )
else:
    try:
        from pgmpy.parameter_estimator import DiscreteMLE
        bn.fit(df, estimator=DiscreteMLE())
    except (ImportError, TypeError):
        from pgmpy.estimators import MaximumLikelihoodEstimator
        bn.fit(df, estimator=MaximumLikelihoodEstimator)
```

The branch is selected by `self.param_method`, set at construction time
(line 30 default `"mle"`). The `try/except` for `DiscreteMLE` is a
version-compatibility fallback; both `DiscreteMLE` and
`MaximumLikelihoodEstimator` are pure counting MLE.

> **Inaccuracy in the original #43 body**: the body claims pgmpy uses
> `equivalent_sample_size=1`. Actual code uses `=5`, the documented pgmpy
> default ([upstream docs](https://pgmpy.org/param_estimator/bayesian_est.html)).
> The MLE-equivalence math at `n_train=10000`, `cardinality=4`: BDeu prior
> contributes `5 / (4·4) = 0.3125` pseudocounts per CPT cell vs `~625` real
> counts/cell = ~0.05% of posterior mass. Bit-identical at float precision is
> mathematically *plausible* even if the bayes branch ran. (It does not.)

`nbn-cat` and `nbn-neuralcat` route through distinct `Mechanism` subclasses:

| | `CategoricalTableMechanism` (`nbn/mechanisms/categorical_table.py:58-134`) | `NeuralCategoricalMechanism` (`nbn/mechanisms/neural_categorical.py:53-96`) |
|---|---|---|
| Parameterization | Dense CPT (`nn.Parameter` of shape `[prod(pa_cards), K]`) | MLP (`nn.Module`) over float-cast parent indices, plus root `nn.Parameter` |
| Fit | Closed-form counting MLE via `scatter_add_`, optional Dirichlet(α) smoothing (default α=0) | Adam SGD on cross-entropy, default `epochs=100` (caller passes 20) |
| Storage | `self._logits` | `self.net` (non-root) + `self._root_logits` (root); no `_logits` attr |
| Honors `epochs/lr/batch_size`? | No (ignored kwargs) | Yes |

The shared base `Mechanism.fit_local` (`nbn/mechanisms/base.py:108`) is an
`@abstractmethod` — pure interface, no shared implementation.

### 2. Empirical bit-identity in the v0.6c-d parquet

```python
import pandas as pd
df = pd.read_parquet('benchmarking/results/raw/parameter_learning_paper_metrics.parquet')
ok = df[(df['status'] == 'ok') & (df['family'] == 'discrete') & (df['metric'] == 'tv_per_node')]
piv = ok.pivot_table(index=['n_nodes','seed'], columns='baseline', values='value', aggfunc='first')

(piv['nbn-cat']   - piv['nbn-neuralcat']).abs().max()  # 0.0  (24/24 cells)
(piv['pgmpy-mle'] - piv['pgmpy-bayes']  ).abs().max()  # 0.0  (25/25 cells)
```

For pgmpy, bit-identity at `equivalent_sample_size=5` is mathematically *plausible*
but unconfirmed without verifying the bayes branch actually ran. For NBN, bit-identity
across 24 cells is **not plausible** under SGD-vs-counting — gradient descent at
20 epochs converges *near* MLE but not bit-identically.

`total_time_s` for the same cells: `nbn-neuralcat` is on average 1.4× slower than
`nbn-cat` (max 5.5×). This initially looked like evidence for distinct dispatch, but
with both running `CategoricalTableMechanism` the variance is process-level noise
on small per-cell counting loops (a few ms each).

### 3. Runner-level smoking gun

`benchmarking/crash_test_runner.py:run_parameter_learning` (line 158-210) loops
over baseline specs:

```python
# line 173
label  = _label_from_spec(spec)             # 'nbn-cat' / 'nbn-neuralcat' / 'pgmpy-mle' / 'pgmpy-bayes'
# line 190
legacy = _legacy_adapter_for_spec(spec)     # 'nbn' / 'pgmpy' (polymorphic string)
# line 191-196
cell_rows = run_with_guard(
    lambda f=family, nn=n, ss=s, lg=legacy:
        _param_learning_cell(cfg, f, nn, ss, lg),     # ← dispatched on `legacy`
    family=family, n_nodes=n, seed=s, baseline=label,
    timeout_s=cfg.per_cell_timeout_s,
)
# line 200-201 — relabel after the cell ran
for r in cell_rows:
    r.baseline = label
```

`_param_learning_cell` (line 283-308) dispatches on the legacy string:

```python
# line 300-308
if baseline == "nbn":
    metric, value = _fit_and_score_nbn(cfg, bn, family)
elif baseline == "pgmpy":
    metric, value = _fit_and_score_pgmpy(bn, family)
else:
    raise NotImplementedError(
        f"param-learning baseline {baseline!r} accuracy wiring is v0.5b",
    )
```

So every `nbn-*` baseline → `_fit_and_score_nbn`, and every `pgmpy-*` baseline
→ `_fit_and_score_pgmpy`. The method-keyed label is dropped at the dispatch
site and re-attached after the cell runs.

`_fit_and_score_nbn` (line 417-437) constructs the fitted model via
`fresh_mechanism_for(...)` (`benchmarking/_crash_test_utils.py:482-518`):

```python
# _crash_test_utils.py:504-512
if kind == "discrete":
    if (family == "hybrid" and parent_kinds
            and any(pk == "continuous" for (pk, _) in parent_kinds)):
        return BinningCategoricalTable(...)
    return CategoricalTableMechanism(alpha=0.0)
```

`NeuralCategoricalMechanism` is **never constructed** by `fresh_mechanism_for`.
For the entire `nbn-*` family in parameter-learning, every discrete node is fit
with `CategoricalTableMechanism(alpha=0.0)`.

`_fit_and_score_pgmpy` (line 440-453) constructs the adapter with no kwargs:

```python
# crash_test_runner.py:447
adapter = PgmpyAdapter()
```

`PgmpyAdapter()` defaults `param_method="mle"`. The bayes branch never fires.
Tracked separately as [#53](https://github.com/Giovannibriglia/NeuralBayesianNetworks/issues/53).

### 4. Inference is empirically clean

The inference path uses a separate dispatch — `_inference_cell`
(`crash_test_runner.py:322-409`) routes via `_time_nbn_inference` (line 618) /
`_time_loop_inference` (line 687). `_time_nbn_inference` builds a
`BaselineSpec` from scratch with hardcoded mechanism per family (line 649-663),
then calls `build_adapter_v2(spec, ...)`.

The mechanism-per-family hardcoding has a similar smell to the parameter-learning
bug, but in practice the inference parquet's method-keyed pairs differ
empirically:

| pair (inference parquet) | family / metric | max abs diff (cells) |
| --- | --- | --- |
| `nbn-mdn-lw` vs `nbn-flow-lw` | continuous_nongauss / accuracy | 1.6e-2 (10) |
| `nbn-cat-lw` vs `nbn-neuralcat-lw` | discrete / accuracy | 2.3e-2 (25) |
| `nbn-lg-lw` vs `nbn-mdn-lw` | continuous_lg / accuracy | 3.3e-2 (25) |
| `pgmpy-mle-ve` vs `pgmpy-bayes-ve` | discrete / accuracy | 4.3e-2 (20) |
| `pgmpy-mle-ve` vs `pgmpy-bayes-ve` | discrete / total_time_s | 7.7e+0 (20) |

The 7.7-second `total_time_s` delta between `pgmpy-mle-ve` and `pgmpy-bayes-ve`
is decisive: BayesianEstimator carries real per-cell cost relative to
MaximumLikelihoodEstimator, so they're running different pgmpy estimators in
the inference path.

This audit does **not** trace the inference dispatch in full — empirical
distinction is enough to rule out the parameter-learning's "max abs diff = 0.0"
pattern. A separate inference-side audit is not warranted.

## Diagnosis

**Diagnosis B (parameter-learning runner-side bug).**

- `nbn-cat` and `nbn-neuralcat` rows in the v0.6c-d parameter-learning parquet are bit-identical because both routes invoke `CategoricalTableMechanism(alpha=0.0)` via `fresh_mechanism_for`.
- `pgmpy-mle` and `pgmpy-bayes` rows are bit-identical because both routes invoke `PgmpyAdapter()` with default `param_method="mle"`.
- The parquet's method-keyed `baseline` column is post-hoc relabeling, not dispatch evidence.

The v0.6c-d **inference** parquet is unaffected by this specific bug.

## Implications for v0.6c-d paper data

| Claim | Honest? |
| --- | --- |
| `nbn-cat` 2.3× more accurate than `pgmpy-mle` on discrete at scale (TV ≈ 0.14 vs 0.34) | **Yes** — `nbn-cat` is `CategoricalTableMechanism`; `pgmpy-mle` is pgmpy's MLE. Distinct fit paths. |
| `nbn-lg` matches `pgmpy-lg` quality on `continuous_lg` (W₁ ≈ 0.083) | **Yes** — different family / different code path; `LinearGaussianMechanism` vs pgmpy's LGBN. Unaffected by this audit. |
| Hybrid family is NBN-only territory (`nbn-hybrid` 25/25 cells, W₁ ≈ 0.08-0.10) | **Yes** — `_fit_and_score_nbn` → `BinningCategoricalTable` (discrete sub-targets) + `LinearGaussianMechanism` (continuous). Real fit, just not method-keyed. No competitor library has applicable hybrid baselines. |
| `nbn-neuralcat` and `pgmpy-bayes` rows in the parameter-learning parquet | **Misleading** — these are not method-distinct evaluations. They are duplicate rows of `nbn-cat` / `pgmpy-mle` with method-keyed labels reapplied post-hoc. |

## Future runs

After the v0.8 fix (#51 + #52 + #53):

- `nbn-neuralcat` (parameter-learning): will produce *different* TV values from
  `nbn-cat`. Probably worse, since `NeuralCategoricalMechanism` has the latent
  root-node bug (#52) and SGD-near-MLE drift; the MLP parameterization may also
  underperform direct counting on small datasets.
- `pgmpy-bayes` (parameter-learning): will produce TV values very close to but
  not bit-identical with `pgmpy-mle`, since BDeu at ESS=5 contributes ~0.05% of
  posterior mass at `n_train=10000`.
- `nbn-cat` and `pgmpy-mle`: unchanged.
- All inference rows: unchanged.

If a paper rerun is desired post-fix, expect ~18 hours on the same RTX 4070
Laptop hardware. The headline 2.3× quality finding is unchanged.
