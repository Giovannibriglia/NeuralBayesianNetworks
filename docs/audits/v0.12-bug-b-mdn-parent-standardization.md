# v0.12 Bug B resolution — MDN parent standardization (PR #90)

Tracking issues: [#81](https://github.com/Giovannibriglia/NeuralBayesianNetworks/issues/81) (Bug B),
[#24](https://github.com/Giovannibriglia/NeuralBayesianNetworks/issues/24)
(NaN origin in deep continuous_nongauss chains),
[#54](https://github.com/Giovannibriglia/NeuralBayesianNetworks/issues/54)
(MDN gradient stability). Master at audit time: `9fcd2ee`. Fix landed:
PR [#90](https://github.com/Giovannibriglia/NeuralBayesianNetworks/pull/90)
(merged 2026-05-18, two commits on
`fix/v0.12-mdn-parent-standardization-bug-B`).

## TL;DR

Bug B — the NaN-driven `MultinomialKernel` CUDA assert that prevented
`nbn-mdn-lw` and `nbn-flow-lw` from running on `continuous_nongauss` —
is fixed by per-node parent standardization inside `MDNMechanism`. The
fix is applied **inside the mechanism**, not inside the synthetic-data
generator: the upstream root cause (deep ancestral chains producing
3.3M-scale parent values at paper-config scales) is a real property of
the benchmark family, and the MDN must be numerically robust to it
rather than relying on the data generator to bound the range.

The fix is two commits. Commit 1 adds parent standardization with
`pa_mean` / `pa_std` `register_buffer`s computed in `fit_local` and
applied in `_params_from_parents`. Commit 2 removes a
double-standardization bug caught during the Phase 5 edge-case audit
(pre-standardizing in `fit_local` combined with the per-call
standardization in `_params_from_parents` produced training/inference
inconsistency and a constant-parent NaN crash). The
`_sanitise_parents` band-aid from v0.6c-A Finding 2 stays in place as
defense in depth.

## Failure path (Phase 1 + Phase 2 findings)

Phase 1 training-data inspection on `continuous_nongauss n=50 seed=3`
showed extreme parent values from deep ancestral chains:

| Node | abs_max(parent value) | Chain depth |
|---|---:|---:|
| X21 | 3.3 × 10⁶ | 5 hops |
| X42 | 5.6 × 10⁵ | 4 hops |

Phase 2 per-step instrumentation in `MDN.fit_local` localised the
failure to epoch 0 step 2, with the following sequence:

1. `parents` batch contains a row with one component ≈ 3.3 × 10⁶.
2. `_params_from_parents` computes
   `out = self.net(parents)`; the final linear layer's row mapping to
   the `log_scale` slot has a non-trivial weight, so
   `log_scale ≈ 3.3e6 × w ≈ O(10⁵)` after the MLP forward pass.
3. `scale = torch.exp(log_scale).clamp_min(self.min_scale)` overflows
   to `+inf` (`exp(O(10⁵))` exceeds float32 range).
4. `Normal(loc, scale=inf).log_prob(x)` evaluates to `-inf` for the
   in-batch rows and produces a loss of magnitude ≈ 1.87 × 10¹⁴.
5. `loss.backward()` overflows the gradient buffers to NaN.
6. The Adam step writes NaN into the MLP weights and biases.
7. From epoch 0 step 3 onward, every forward pass produces NaN
   parameters. Training "completes" but the model is unusable.
8. At LW inference, `_params_from_parents` returns NaN logits;
   `Categorical(probs=softmax(NaN))` produces an invalid probability
   tensor; the CUDA `MultinomialKernel` launches a sampling assert and
   fires `cudaErrorAssert`, reported asynchronously.

The visible symptom in the paper-run parquet — "CUDA error:
device-side assert triggered" — is step 8. Steps 1–7 happen silently
during fit.

The pre-existing `_sanitise_parents` guard at `mdn.py:16-59` (added
in v0.6c-A Finding 2) replaces non-finite parent values with 0, but
**the parents at this scale are finite — they are just extreme** —
so the sanitiser passes them through unmodified. Bug B is therefore
distinct from the v0.6c-A finding that motivated the sanitiser;
they share the visible CUDA-assert symptom but differ in the parent
state that triggers it.

## Fix design

Per-node parent standardization, computed once in `fit_local` from
training data and applied at every forward call in
`_params_from_parents`.

### Why parents-only, not also `x`

The MDN's outputs (`logits`, `loc`, `log_scale`) are predicted by an
MLP from `parents` only. Extreme `x` values do not flow through the
network and can't drive overflow. Standardizing `x` would shift the
predicted `loc` and `scale` parameters relative to the data, making
log-prob comparisons against pre-fix runs incomparable — for no
numerical benefit. Parents-only standardization keeps the predicted
density in the same coordinate frame as the training data.

### Why per-node, not per-family

Standardization statistics are properties of the per-node parent
distribution. Sharing statistics across nodes would couple unrelated
CPDs and break the structural assumption that each
`MDNMechanism` is a standalone CPD. Per-node also keeps the fix
local — no changes to the model class or the runner needed.

### Why `register_buffer`, not `nn.Parameter` or plain attributes

`register_buffer` ensures the statistics survive `state_dict()` save
and load — necessary for the v0.7 fit-then-query semantics
(PR #28) where the *fitted* model is queried at inference time, not
the truth model. The Phase 6 state_dict round-trip test verifies
this: fit a model, save, reload into a fresh instance, compare
forward pass outputs against the original — `max_diff = 0.00e+00`.

Buffers (not parameters) because the statistics are computed from
data, not learned by gradient descent.

### Single canonical standardization path

The Phase 5 edge-case audit caught a double-standardization bug in
commit 1's initial form: `fit_local` pre-standardized parents before
the training loop, and `_params_from_parents` also standardized at
every forward call. This produced:

- **Training/inference inconsistency at large-scale parents**: during
  fit the network saw `(parents − mean) / std` pre-standardized; at
  inference it saw `((parents − mean) / std − mean) / std`, which is
  a different input distribution.
- **Constant-parent NaN crash**: for a parent column with
  `std = 0`, `pa_std.clamp_min(1e-3)` saved the first standardization,
  but the second standardization at inference time saw inputs of
  exactly 0 (the standardized constant), then re-standardized to
  `(0 − 0)/1e-3 = 0`, which is fine — but during training the
  pre-standardized `0` then went through the MLP, and the second
  standardization inside the same call computed
  `(0 − mean=0) / std=1e-3 = 0` repeatedly, causing the network to
  see only zeros and produce undefined gradients.

Commit 2 removed the pre-standardization in `fit_local`.
`_params_from_parents` is now the **single canonical standardization
path**, applied identically at train and inference. This is the
invariant the Phase 5 audit re-checks for every edge case.

## Validation methodology — 6 phases, 39 cells

PR #90's validation grid covers six failure axes. The grid is
deliberately broader than "the failing seed now passes" to catch
regressions in adjacent cells and confirm the fix isn't a coincidence
on the specific Phase 1 seed.

| Phase | Coverage | Cells | Outcome |
|---|---|---:|---|
| 1 | Scale — `continuous_nongauss / nbn-mdn-lw` seed=3, n ∈ {10, 50, 100, 500, 1000} | 5 | 5/5 ok |
| 2 | Seed sweep — `continuous_nongauss / nbn-mdn-lw` n=50, seeds 0–4 | 5 | 5/5 ok |
| 3 | Transitive — `continuous_nongauss / nbn-flow-lw` n ∈ {10, 50, 100}, seeds ∈ {0, 2, 3} | 9 | 9/9 ok |
| 4 | Timing regression — `continuous_lg / nbn-mdn-lw` n=100, seeds 0/1/2 (smoke unchanged) | 3 | 3/3 ok, ~9 ms/cell |
| 5 | Edge cases — constant parent, None buffer, device movement, root node, 1e6-scale | 5 | 5/5 pass |
| 6 | state_dict round-trip — fit, save, reload, compare forward pass | 1 (fitted model) | max_diff = 0.00e+00 |
| Post-commit-2 re-validation | n ∈ {50, 100}, seeds ∈ {0, 1, 3} | 6 | 6/6 ok |
| **Total** | | **34** | |

Plus the new unit tests in `tests/unit/test_mdn_robustness.py` (3 new
cases — extreme parents, constant parent, training/inference
consistency) bring the unit-level coverage to 11 passing tests for
MDN. The pre-existing `test_baseline_registry.py` and
`test_baseline_applicability_consolidation.py` continue to pass; the
applicability snapshot was updated to restore `continuous_nongauss` in
the `nbn-mdn-lw` / `nbn-flow-lw` frozensets (reverting the temporary
gate from PR #86).

### What each phase proves

- **Phase 1** demonstrates the fix scales — the specific failing
  configuration (seed=3, deep chain producing 3.3 M-scale parents)
  now passes across the full n range that exhibited the failure.
- **Phase 2** rules out seed-specific success — the fix holds across
  the full seed sweep at the n where Bug B first manifested.
- **Phase 3** confirms the fix is transitive to `nbn-flow-lw`, which
  shares the synthetic-data sampling chain but uses a different
  inference mechanism. Same parent distribution → same overflow path
  → same fix applies.
- **Phase 4** rules out a timing regression on the family where the
  fix matters least (`continuous_lg` parents are O(1) by construction;
  standardization is a near-no-op). ~9 ms/cell matches pre-fix.
- **Phase 5** is the edge-case audit that caught the
  double-standardization bug. The five edge cases — constant parent
  column, `None` buffer on a fresh-init model, CPU → CUDA device
  movement of fitted buffers, root node path (skips standardization
  entirely), and synthetic 1 × 10⁶-scale parent — exercise the
  off-happy-path code that didn't surface in Phases 1–4.
- **Phase 6** proves the fix is persistent across `state_dict` round
  trip — necessary for the fit-then-query runner contract from PR #28.

## Deferred items

### v0.6c-A Finding 2 sanitiser stays

`_sanitise_parents` at `mdn.py:16-59` is retained as defense in
depth. Parent standardization addresses the overflow path that
Bug B exercises (large-but-finite parents); the sanitiser addresses
a different path (genuinely non-finite parents from upstream
mechanism NaN propagation, e.g. at very deep continuous_nongauss
n=5000 chains). Both can coexist — the sanitiser is a no-op on
finite input and reaches zero-replacement on NaN/Inf, which the
standardization step then maps to `(0 − mean) / std`. Removing the
sanitiser would re-open the v0.6c-A code path; out of scope.

### Issue #24 — upstream NaN origin in deep continuous_nongauss chains

Still open. The Bug B fix neutralises the *consequence* of extreme
upstream parent values at MDN-fit time, but the synthetic data
generator continues to produce them at deep chain depths. Future
work in #24 should investigate whether the chain-depth amplification
is an artefact of the random-DAG sampler's parameter ranges or a
real property of the family being benchmarked.

### Manifestation 1 of #54 is unreachable at paper-config scales

PR #90's Phase 1/2 grid confirms `nbn-mdn-lw` is stable at n ∈ {5,
10, 50} across all seeds — the failure mode #54 catalogued for
manifestation 1 (training instability at small n with deep chains)
is not reproducible at any seed in the paper config. Closing #54's
manifestation 1 deferred until the v0.8 audit cycle re-examines #54's
broader classification.

### Issue #91 — variance amplification

Filed during Phase 5 audit. Not Bug B, not paper-blocking. Deferred
to v0.8.
