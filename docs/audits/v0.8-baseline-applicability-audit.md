## TL;DR

Pre-Pass-10 the codebase carried **three** independent applicability gates:
the canonical per-label registry (`_BASELINE_APPLICABILITY` in
`benchmarking/_baseline_registry.py`), a legacy adapter-keyed negative-list
(`_NOT_APPLICABLE` in `crash_test_runner.py:111-126`), and an
accuracy-row-only gate (`_ACCURACY_NOT_APPLICABLE` at lines 129-144).
The latter two were mid-refactor debt since the v0.6c-C-1a → C-1b
transition; the comment at `crash_test_runner.py:198` flagged the
dual-gating as known. The Pass-10 priority-1 consolidation (PR #65)
collapsed all three into a single `BaselineApplicability` frozen
dataclass exposing `families: frozenset[str]` and
`accuracy_supported: bool = True`, with the runner's pre-dispatch gate
remaining the only enforcement point.

This audit documents the **canonical applicability matrix as of the
post-consolidation state**, classifies the 66 not-applicable (label,
family) cells into four buckets — structural / Pass-10-lifted /
Pass-10-pending / pending-investigation — and records two open
operational findings that surfaced during the consolidation work
(the zuko `ElementWiseTransform` API incompatibility tracked as
issue #66, and the CI smoke-budget tightening that motivated PR
#65's commit 256dbb9). Paper readers asking "why doesn't X run on Y?"
should find their answer in §4-7 below; the matrix in §3 is the
single source of truth.

## §4 Structural restrictions

54 of the 66 not-applicable cells are structural: the mechanism and family
are mathematically incompatible.  No amount of adapter wiring lifts
these — the restriction is in the math, not the implementation.
Eight sub-buckets, grouped by structural reason.

### §4.1 GpyTorch capacity limits — GPs require continuous latents

Gaussian processes parameterise continuous functions; discrete latents
require a fundamentally different machinery (EP / variational
classifiers / GPClassifier).  The current `GPyTorchAdapter` runs only
`ApproximateGP` with a Gaussian likelihood and explicitly refuses
discrete evidence at `benchmarking/baselines/gpytorch_adapter.py:76`
(`raise NotImplementedError("gpytorch adapter cannot condition on
discrete evidence")`).  Hybrid families share the same restriction —
their discrete components have no GP representation.

The cells are also `accuracy_supported=False` on the continuous
families where they DO apply (§3 matrix).  Note the symmetry: the GP
"fit" path is a trainer pass that mostly measures fit-time, not
parameter quality — both `gpytorch-gp` (param-learning side) and
`gpytorch-gp-predict` (inference side) carry the
`accuracy_supported=False` flag for the same reason.

**4 cells:**

| Label | Family | Reason |
|---|---|---|
| `gpytorch-gp`         | discrete | GP needs continuous latents |
| `gpytorch-gp`         | hybrid   | hybrid has discrete components |
| `gpytorch-gp-predict` | discrete | (same) |
| `gpytorch-gp-predict` | hybrid   | (same) |

### §4.2 Exact VE engine requires tabulated CPDs

`TensorVariableElimination` (`nbn/inference/tensor_ve.py:29-30`,
"Log-domain VE for discrete BNs") operates on log-domain einsum over
tabulated factors.  Continuous targets have no tabulated CPD —
density-vs-density elimination is a different algorithm
(Gaussian VE, particle-based MP).  The engine explicitly rejects
non-discrete mechanisms at `tensor_ve.py:59-61`:
`if not mech.is_discrete: raise ValueError(
"TensorVariableElimination only supports discrete mechanisms; ...")`.
This restriction is **engine-side**, not mechanism-side: the
underlying NeuralCategoricalMechanism is tabulatable per Pass 8 PR #63
(`Mechanism.tabulate(parent_cards)`), but its tabulation produces a
discrete distribution by definition.

**6 cells:**

| Label | Family | Reason |
|---|---|---|
| `nbn-cat-ve`         | continuous_lg       | VE engine needs tabulated CPDs |
| `nbn-cat-ve`         | continuous_nongauss | (same) |
| `nbn-cat-ve`         | hybrid              | hybrid has continuous components |
| `nbn-neuralcat-ve`   | continuous_lg       | (same as nbn-cat-ve) |
| `nbn-neuralcat-ve`   | continuous_nongauss | (same) |
| `nbn-neuralcat-ve`   | hybrid              | (same) |

### §4.3 Linear Gaussian mechanism — Gaussian on discrete/non-Gaussian

`LinearGaussianMechanism` (`nbn/mechanisms/linear_gaussian.py:13-27`,
`is_discrete: bool = False`) parameterises `Normal(β₀ + Σᵢ βᵢ·paᵢ, σ²)`.
This is closed under linear combinations of Gaussians only.  Discrete
targets have no Gaussian likelihood; non-Gaussian continuous targets
violate the linear-Gaussian closure (no σ² that matches the true
density).  The pgmpy `LinearGaussianBN` family at
`benchmarking/baselines/pgmpy_adapter.py:24` (with v0.7 fix tracking)
inherits the same restriction.

**10 cells:**

| Label | Family | Reason |
|---|---|---|
| `nbn-lg`            | discrete            | LG mechanism, no Gaussian over categorical |
| `nbn-lg`            | continuous_nongauss | LG closure broken by non-Gaussian density |
| `nbn-lg`            | hybrid              | discrete components have no LG form |
| `nbn-lg-lw`         | discrete            | (same as nbn-lg) |
| `nbn-lg-lw`         | continuous_nongauss | (same) |
| `nbn-lg-lw`         | hybrid              | (same) |
| `pgmpy-lg`          | discrete            | pgmpy LinearGaussianBN is Gaussian-only |
| `pgmpy-lg`          | continuous_nongauss | (same) |
| `pgmpy-lg-predict`  | discrete            | (same as pgmpy-lg) |
| `pgmpy-lg-predict`  | continuous_nongauss | (same) |

(`pgmpy-lg` and `pgmpy-lg-predict` on **hybrid** are in §7 — Phase 0.5
showed they numerically run; semantic verification pending.)

### §4.4 Categorical mechanisms — discrete on continuous data

`CategoricalTableMechanism` (`nbn/mechanisms/categorical_table.py:16`,
`is_discrete: bool = True`) and `NeuralCategoricalMechanism`
parameterise distributions over integer class labels.  Continuous
data has no class label — fitting / sampling / evaluating
`log P(x | parents)` for `x ∈ ℝ` is undefined under a categorical
model.  Sibling LW inference variants (`-lw`) inherit the
mechanism-level restriction.  Note `-ve` variants on continuous
are double-blocked (engine AND mechanism) and live in §4.2.

**12 cells:**

| Label | Family | Reason |
|---|---|---|
| `nbn-cat`            | continuous_lg, continuous_nongauss, hybrid | categorical CPD, no continuous classes |
| `nbn-neuralcat`      | continuous_lg, continuous_nongauss, hybrid | (same) |
| `nbn-cat-lw`         | continuous_lg, continuous_nongauss, hybrid | (same) |
| `nbn-neuralcat-lw`   | continuous_lg, continuous_nongauss, hybrid | (same) |

### §4.5 pgmpy DiscreteBN — discrete-only base class

`pgmpy.models.DiscreteBayesianNetwork` is a separate class from
`LinearGaussianBN`; the former holds `TabularCPD` objects only.
Continuous families have no `TabularCPD` representation without
discretization (which the adapter doesn't perform).  Hybrid would
require pgmpy's `ConditionalLinearGaussianBN` — that's the Pass 10
priority-4 candidate in §6, not blocked by structural impossibility
but by adapter wiring.

**8 cells:**

| Label | Family | Reason |
|---|---|---|
| `pgmpy-mle`       | continuous_lg, continuous_nongauss | DiscreteBN is categorical-only |
| `pgmpy-bayes`     | continuous_lg, continuous_nongauss | (same) |
| `pgmpy-mle-ve`    | continuous_lg, continuous_nongauss | (same) |
| `pgmpy-bayes-ve`  | continuous_lg, continuous_nongauss | (same) |

(`pgmpy-mle/bayes/-ve` on **hybrid** are in §6 — Pass 10 priority-4

### §4.6 Pyro adapter scope — empirical + LG only

`PyroAdapter` (`benchmarking/baselines/pyro_adapter.py:52`) wraps an
ancestral generative model with two supported CPD types: empirical
(Laplace-smoothed counts for discrete) and linear-Gaussian
(`Normal(β₀ + Σᵢ βᵢ·paᵢ, σ)` per the #32 fix).  Non-Gaussian
continuous needs SVI with a parameterised guide — out of adapter
scope.  Hybrid networks would require dispatching the mixed-parent
case across the two CPD types within one generative model; also out
of current scope.

**4 cells:**

| Label | Family | Reason |
|---|---|---|
| `pyro-empirical`             | continuous_nongauss, hybrid | adapter covers empirical-discrete + LG only |
| `pyro-empirical-importance`  | continuous_nongauss, hybrid | (same) |

### §4.7 Hybrid mechanism / router — only meaningful on hybrid families

**Note**: §4.7 differs from the other §4 sub-buckets in *kind*.  The
preceding restrictions (§4.1-§4.6) and the following one (§4.8) are
mathematical incompatibilities — running the cell would crash or
produce undefined output.  §4.7's cells DO run without error
(Phase 0.5 confirmed `nbn-hybrid` and `-router` on continuous_lg
execute), but the registry rejects them because the hybrid router
degenerates to a single-mechanism dispatch on non-hybrid families —
producing a paper-misleading result that looks like a fresh baseline
but is actually a copy of `nbn-cat` / `nbn-lg`.  This is the
"registry encodes intent" concern that the architectural note in
§9 will address.  Distinguish from §7's "numerically runs but
semantically questioned" (pgmpy-lg on hybrid): §4.7 is *degenerate
equivalence* (the cell IS another baseline); §7 is *dubious values*
(the cell produces numbers whose meaning is unclear).

`nbn-hybrid` (param-learning) and `nbn-hybrid-router` (inference,
`nbn/inference/hybrid.py:15` `class HybridRouter`) are dispatch
abstractions over **mixed** discrete + continuous components.  On a
pure-discrete or pure-continuous family the router has nothing to
route — the cell would degenerate to a single-mechanism dispatch,
which the registry already covers via `nbn-cat`, `nbn-lg`, etc.

**6 cells:**

| Label | Family | Reason |
|---|---|---|
| `nbn-hybrid`         | discrete, continuous_lg, continuous_nongauss | hybrid router degenerate on non-hybrid |
| `nbn-hybrid-router`  | discrete, continuous_lg, continuous_nongauss | (same) |

### §4.8 Continuous mechanisms (MDN, normalizing flow) — no discrete output

`MDNMechanism` (`nbn/mechanisms/mdn.py:78-103`, `is_discrete: bool =
False`) parameterises a mixture-of-Gaussians density over `ℝ`;
`NormalizingFlowMechanism` (`nbn/mechanisms/normalizing_flow.py:37-60`,
`is_discrete: bool = False`) parameterises a learned bijection from a
base distribution to a continuous target distribution.  Neither
produces a density over a finite discrete alphabet — the mathematical
output space is wrong.  Symmetric to §4.4 (categorical mechanisms on
continuous): both directions are blocked by the same is_discrete
flag's incompatibility with the family's target type.

**4 cells:**

| Label | Family | Reason |
|---|---|---|
| `nbn-mdn`     | discrete | MDN output is a continuous mixture density |
| `nbn-flow`    | discrete | flow output is a continuous bijection |
| `nbn-mdn-lw`  | discrete | (same as nbn-mdn) |
| `nbn-flow-lw` | discrete | (same as nbn-flow) |

## §6 Pass-10-pending restrictions (lift-by-wiring candidates)

10 of the 66 not-applicable cells could be lifted by extending
existing adapters or wiring new ones — the underlying library
supports the family-mechanism combination, but the codebase's
adapter hasn't connected it yet.  Two wiring tracks, both queued
as Pass 10 priorities 3 and 4.

### §6.1 Pomegranate continuous wiring (priority-3, 6 cells)

`pomegranate` v1.x (PyTorch-backed BayesianNetwork module, per the
adapter docstring at `benchmarking/baselines/pomegranate_adapter.py:1-7`)
ships continuous distribution classes (`Normal`, `Categorical`,
mixtures).  The current adapter exposes only the discrete path
(`supports = {"discrete"}`, per its module docstring's explicit
scope note), so continuous targets fall through to a
`not_supported` row.  Wiring the continuous case is a single-
adapter task: instantiate the appropriate pomegranate distribution
per node, fit via pomegranate's `fit` method, expose `predict_proba`
for inference.

**6 cells:**

| Label | Family | Lift-by |
|---|---|---|
| `pomegranate-discrete`     | continuous_lg | extend adapter with continuous distribution dispatch |
| `pomegranate-discrete`     | continuous_nongauss | (same; non-Gaussian continuous via mixture distributions) |
| `pomegranate-discrete`     | hybrid | (same; mixed-parent case via pomegranate's joint factor types) |
| `pomegranate-discrete-ve`  | continuous_lg | (inference-side, same adapter extension) |
| `pomegranate-discrete-ve`  | continuous_nongauss | (same) |
| `pomegranate-discrete-ve`  | hybrid | (same) |

Note on the label name: `pomegranate-discrete` reflects the current
adapter's scope, not pomegranate's library capability.  When
continuous is wired (priority-3), the label naming becomes a design

parquet consumers, requires migration), or add `pomegranate-continuous`
as a parallel label (preserves backward compat, adds matrix entries).
Both options keep v0.6c-d paper rows valid; priority-3 chooses.

### §6.2 pgmpy DiscreteBN variants on hybrid (priority-4 candidate)

pgmpy v1.x has `DiscreteBayesianNetwork`, `LinearGaussianBN`, and

Hybrid families have mixed discrete + continuous components, which
CLG can represent (continuous children conditioned on discrete +
continuous parents).  The current `PgmpyAdapter` doesn't dispatch
CLG — Pass-10 priority-4 work would investigate whether pgmpy's
CLG class ships a usable inference engine alongside the model, and
wire it if so.

**4 cells:**

| Label | Family | Lift-by |
|---|---|---|
| `pgmpy-mle`       | hybrid | wire pgmpy CLG fit; mle-style MLE for both discrete and continuous components |
| `pgmpy-bayes`     | hybrid | wire pgmpy CLG fit with Bayesian-prior estimator |
| `pgmpy-mle-ve`    | hybrid | wire pgmpy CLG VE inference (depends on CLG inference engine availability) |

### §7.1 pgmpy-lg variants on hybrid — numerically works, semantics questioned (2 cells)

Pass-10 priority-1's Phase 0.5 reachability investigation showed
that both `pgmpy-lg` (param-learning) and `pgmpy-lg-predict`
(inference) execute on hybrid families without crashing, emitting
all 4-5 metric rows with `status='ok'`.  This was unexpected:
pgmpy's `LinearGaussianBN` is Gaussian-only by construction, and
hybrid families contain discrete components that have no LG
representation.  Two interpretations are possible:

1. **Adapter projects hybrid → continuous-only correctly**: pgmpy
   silently drops or marginalises out discrete components,
   producing a continuous-component-only fit that is semantically
   meaningful (just incomplete).  Metric values would be honest
   on the continuous subset.

2. **Adapter misinterprets discrete components as continuous**:
   pgmpy reads the discrete columns as floats and fits LG mechanisms
   over them, producing numerically-valid but semantically-wrong
   parameters.  Metric values would be honest-bad
   (low TV / W₁ / JSD against the true hybrid model, but for the
   wrong reason).

Distinguishing requires comparing pgmpy-lg vs nbn-lg metric values
on the same hybrid cell — if shapes agree, interpretation (1) is
likely correct and the cells are registry-promotable; if they
diverge, interpretation (2) is correct and the cells stay
non-applicable.

**This reframes Pass-10 priority-4 from "wire pgmpy CLG for
hybrid" to "investigate pgmpy-lg hybrid semantics, THEN wire
CLG if-and-only-if pgmpy-lg hybrid is correctly projecting."**
The investigation has to happen before the wiring decision, not
as part of it — if pgmpy-lg hybrid is interpretation (2), CLG
might be the only correct path, but if interpretation (1), CLG
is one option among several (a documented lg-on-hybrid mode might
suffice).

**2 cells:**

| Label | Family | Status |
|---|---|---|
| `pgmpy-lg`         | hybrid | numerically runs; semantic verification needed |
| `pgmpy-lg-predict` | hybrid | (same; inference side shares the LinearGaussianBN representation) |

### §7.2 nbn-flow — registry-applicable, blocked by zuko API (3 ✓ caveat cells)

`nbn-flow` is registered as applicable to `{continuous_lg,
continuous_nongauss, hybrid}` per the §3 matrix.  Its current
implementation (`nbn/mechanisms/normalizing_flow.py`) depends on
zuko 1.6.0's `ElementWiseTransform.forward`, which has been
restructured: the attribute `self.hyper` referenced at the
`d_pa == 0` (zero-parent / continuous root node) path no longer
exists.  The failure site is `normalizing_flow.py:127`
(`loss = -self._flow(torch.zeros(bx.shape[0], 0, device=device)).log_prob(bx).mean()`)
inside the `d_pa == 0` branch at line 121 of `fit_local` (line 97).
Issue **#66** tracks the fix.

The runner's `run_with_guard` catches the crash and emits a
`not_supported` row at runtime, so CI doesn't fail hard — but
cells produce zero data until #66 lands.  The registry entry is
correct (the architectural intent is unchanged); the mechanism
implementation needs a fix.  Three (label, ✓-family) pairs are
currently broken:

**3 cells (✓ in §3 matrix; runtime-broken):**

| Label | Family | Block |
|---|---|---|
| `nbn-flow` | continuous_lg       | zuko `ElementWiseTransform.hyper` access; issue #66 |
| `nbn-flow` | continuous_nongauss | (same; same code path) |
| `nbn-flow` | hybrid              | (same; this is the family that surfaced the bug in PR #65 Phase 0.5 verification) |

Inference-side `nbn-flow-lw` is **not** affected by #66 itself: LW
inference uses `sample` / `log_prob` on the fitted model and never
triggers `fit_local`'s `d_pa == 0` branch.  However, all `nbn-flow-lw`
cells are blocked downstream of #66 because they need a fitted
`nbn-flow` model upstream.  And `nbn-flow-lw` on hybrid is
*independently* blocked at fit time by #69 — see §7.4.

### §7.3 nbn-mdn / nbn-hybrid param-learning on hybrid — scoring crash (2 ✓ caveat cells)

PR #65's Phase 0.5 reachability investigation tested hybrid additions
at n=5 only.  The smoke parquet from PR #65's CI (n_nodes ∈ {5, 10})
revealed a scoring-path crash at n=10 hybrid:

```
AttributeError: 'LinearGaussianMechanism' object has no attribute 'n_classes'
  File "benchmarking/crash_test_runner.py", line 546,
  in _build_param_learning_pairs_nbn
```

`_build_param_learning_pairs_nbn` assumes all parents of a discrete
child node are also discrete-categorical when building CPD comparison

**#68** tracks the fix.  At n=5 the randomly-generated DAGs happen to
avoid the failing configuration; at n=10 it surfaces deterministically
under the smoke seed.

The fit step succeeds; only the post-fit scoring crashes.  Affected
cells emit `not_supported` rows at runtime via `run_with_guard`.

| `nbn-hybrid` | hybrid | (same code path; same failure site) |

Suggested fix per issue #68 (three candidates): filter `parent_cards`
by parent kind (partial CPT comparison); skip discrete-child nodes
with mixed-kind parents (per-node `not_supported`); or build a

### §7.4 nbn-*-lw inference fit on hybrid — categorical fit crash (3 ✓ caveat cells)

Companion bug to §7.3, surfaced by the same n=10 smoke parquet.
Inference-side fit on hybrid networks crashes at:

```
RuntimeError: index -4 is out of bounds for dimension 0 with size 8
  File "nbn/mechanisms/categorical_table.py", line 124, in fit_local
    counts.scatter_add_(0, flat_idx, torch.ones(n, device=device))
```

`CategoricalTableMechanism.fit_local` is designed for discrete-only
parents (it indexes into a CPT keyed by parent configurations).  On
hybrid networks where a discrete child has continuous parents, the

arithmetic — `parent_idx` becomes negative, `flat_idx` underflows,
scatter_add_ crashes.  Issue **#69** tracks the fix.  Likely
resolution: switch dispatch to `NeuralCategoricalMechanism` (which
forward-passes over continuous parent values) when discrete children
have continuous parents.

The fit step crashes before any inference / scoring runs.

### §7.5 Operational lesson — verify hybrid additions at multiple n_nodes

PR #65's Phase 0.5 reachability investigation tested only at n=5.
The 5-cell crash documented in §7.3-§7.4 surfaced only at n=10.
Lesson recorded for future Pass-10 priorities (3, 4) and any other
work that promotes registry entries for previously-gated cells:

- **Test at multiple n_nodes values**, not just the smallest.  Hybrid
  DAG shape varies with n; small graphs may avoid configurations that
  larger graphs reliably produce.
- **Reproduce determinism with a fixed seed** at each n value.  The
  five §7.3-§7.4 crashes are seed-0 deterministic at n=10; without
  that property the bugs would be intermittent and harder to track.
- **Examine the smoke parquet**, not just the CI pass/fail status.
  PR #65's CI passed (because `run_with_guard` catches crashes into
  `not_supported` rows) but the parquet showed real broken cells.

The general recommendation lives in §8.4 alongside the cell-count
script; §7.5 records the specific cells (`nbn-mdn` / `nbn-hybrid` /
`nbn-mdn-lw` / `nbn-flow-lw` / `nbn-hybrid-router` on hybrid) that
surfaced the lesson.

## §9 Architectural note — registry encodes three concerns

The post-consolidation `BaselineApplicability` registry is a single
source of truth for **three** semantically distinct concerns that
share one consumer (the dispatch gate at
`crash_test_runner.py:206,257`).  Distinguishing them is the
reader's job, aided by the bucket structure of §§4-7.

### Three concerns, one table

1. **Structural impossibility (§4)** — the mechanism and family are
   mathematically incompatible.  Running the cell crashes or produces
   undefined output.  54 cells in this audit.  Example: `nbn-cat`
   on `continuous_lg` (a categorical CPD has no density over `ℝ`).
   These restrictions are permanent for the current set of
   mechanisms; new mechanisms could lift them by spanning the
   structural gap differently (e.g., a hypothetical
   "categorical-Gaussian" mixture mechanism would not be blocked
   by §4.3 / §4.4 in the same way).

2. **Not-yet-wired (§6)** — the library supports the combination,
   but the codebase's adapter hasn't connected it yet.  10 cells.
   Example: `pomegranate-discrete` on `continuous_lg` (pomegranate
   has `Normal` distributions; the adapter doesn't use them).  These
   restrictions lift when Pass-10+ wiring lands.

3. **Semantic intent (§4.7)** — the mechanism + family combination
   would *run* but produce a paper-misleading result, typically by
   degenerating to a copy of another baseline.  6 cells.  Example:
   `nbn-hybrid-router` on `discrete` (router has nothing to route;
   degenerates to single-mechanism dispatch already covered by
   `nbn-cat`-style baselines).  These restrictions are by *design*
   — they exist to prevent paper readers from seeing two baselines
   that look distinct but are mathematically identical.

§4.7 is the canonical example of concern (3) precisely because
it's the only sub-bucket where the cell would not crash.  §4.7's
framing note flags this explicitly: "registry rejects them because
the hybrid router degenerates to a single-mechanism dispatch on
non-hybrid families — producing a paper-misleading result that
looks like a fresh baseline but is actually a copy of `nbn-cat` /
`nbn-lg`."

### Why one table for three concerns?

The three concerns are semantically distinct but share a single
practical question: *should the runner dispatch this cell?*  The
runner doesn't need to know *why* a cell is not applicable, only
*that* it isn't.  Putting all three in one registry keeps the
runtime gate logic simple (one `is_applicable(label, family)`
check) while pushing the disambiguation question (this audit) to
documentation.  Pass-10+ wiring work can lift §6 cells by editing
the registry; structural restrictions (§4) need the audit doc to
explain "why not"; semantic-intent restrictions (§4.7) need the
audit to record the intent.

### Pending-investigation cases (§7) are a hybrid

The 2 not-applicable cells in §7.1 (pgmpy-lg variants on hybrid)
share characteristics with both concerns (2) and (3): they would
run and produce numbers, but whether those numbers are meaningful
is unclear.  Resolution requires investigation rather than wiring,
which is why §7 is separate from §6.  The 3 ✓ caveat cells in §7.2
(nbn-flow trio) are a fourth shape: registry-correct but
implementation-broken by an external library API change.
