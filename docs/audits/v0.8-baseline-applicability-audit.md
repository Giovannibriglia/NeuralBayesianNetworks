# v0.8 baseline applicability audit

Master at audit time: `58181a1` (post Pass-10-priority-1 merge — PR #65).
Paper-data anchor: tag `v0.6c-d` at commit `2e0dd32` (unchanged by this work).
Branch where audit lands: `docs/v0.10-baseline-applicability-audit`.
Refs: PR #65 (registry consolidation), PR #64 (JSD/W₁ metrics + registry

## TL;DR

Pre-Pass-10 the codebase carried **three** independent applicability gates:
the canonical per-label registry (`_BASELINE_APPLICABILITY` in
`benchmarking/_baseline_registry.py`), a legacy adapter-keyed negative-list
(`_NOT_APPLICABLE` in `crash_test_runner.py:111-126`), and an
accuracy-row-only gate (`_ACCURACY_NOT_APPLICABLE` at lines 129-144).
The latter two were mid-refactor debt since the v0.6c-C-1a → C-1b
transition; the comment at `crash_test_runner.py:198` flagged the
dual-gating as known. The Pass-10 priority-1 consolidation (PR #65)
collapsed all three into a single `BaselineApplicability` frozen
dataclass exposing `families: frozenset[str]` and
`accuracy_supported: bool = True`, with the runner's pre-dispatch gate
remaining the only enforcement point.

This audit documents the **canonical applicability matrix as of the
post-consolidation state**, classifies the 66 not-applicable (label,
family) cells into four buckets — structural / Pass-10-lifted /
Pass-10-pending / pending-investigation — and records two open
operational findings that surfaced during the consolidation work
(the zuko `ElementWiseTransform` API incompatibility tracked as
issue #66, and the CI smoke-budget tightening that motivated PR
#65's commit 256dbb9). Paper readers asking "why doesn't X run on Y?"
should find their answer in §4-7 below; the matrix in §3 is the
single source of truth.

## Scope

This audit is **doc-only**. The runtime consolidation lives in
PR #65; the four hybrid-family applicability additions
(`nbn-mdn`, `nbn-flow`, `nbn-mdn-lw`, `nbn-flow-lw`) ship there.
This document captures the post-cleanup state for cross-reference,
not a fresh code change.

- **v0.6c-d paper artefacts byte-identical**: no scoring code
  touched. The registry consolidation only changes dispatch gating;
  the paper-config and smoke-bench paths exercise unchanged
  code pathways. Verified across all four Pass-10 priority-1
  phases (proof, reachability, consolidation, regression suite).
- **Tag `v0.6c-d` (commit `2e0dd32`)**: unchanged. Re-running the
  v0.6c-d paper config on master `58181a1` produces byte-identical
  parquet for the rows the paper figures consume (`nbn-cat`,
  `pgmpy-mle`, and the inference-side equivalents are untouched
  by this work).
- **Future runs that exercise newly-applicable cells**: the four
  hybrid additions in §5 below mean that re-running the smoke
  config on `58181a1` produces additional rows compared to v0.6c-d.
  These rows are net-new coverage, not changes to existing cells.
